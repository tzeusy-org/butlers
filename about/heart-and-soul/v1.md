# v1 Scope

This document is the scope boundary. If a capability is not named here, it
waits. Scope debates end here; descriptions and status do not live here.

## What v1 Is

One deployment running every agent in `roster/` as a persistent daemon, with
intelligence confined to ephemeral LLM sessions (see
[architecture.md](architecture.md)). v1 has three kinds of parts:

- **Staffers** (infrastructure specialists, excluded from user-message routing
  and briefings): Switchboard (ingress routing), Messenger (outbound delivery),
  QA (error detection and investigation), Concierge (read-only system-plane
  answers, RFC 0030).
- **Domain butlers** (one life domain each, bound by a manifesto): General,
  Health, Relationship, Finance, Education, Travel, Home, Lifestyle, and
  Chronicler (retrospective reconstruction from other butlers' evidence; it
  does not plan, ingest, or notify beyond the daily day-close, and distills
  only into a private schema it owns, RFC 0014).
- **Capabilities** that butlers compose: modules, connectors, the dashboard,
  the identity system, situational awareness (context bus, RFC 0009; proactive
  insight delivery, RFC 0011), and OpenTelemetry observability. The scope
  registry for those is the three name lists below; descriptions and status
  live in [lay-and-land/components.md](../lay-and-land/components.md) and in
  each capability's spec under `openspec/specs/`.

### Modules

Memory, Contacts, Calendar, Email, Telegram, Approvals, Pipeline, Metrics,
Self-healing, Home Assistant, Google Drive, Google Health, WhatsApp, Steam,
Insight broker, Document renderer, Dashboard read (Concierge). Metrics and
Document renderer are loaded by no roster butler today (owner decision
pending in the shape condensation plan).

### Connectors

Telegram bot, Telegram user client, Gmail, Google Calendar, Google Drive,
Google Health, Home Assistant, OwnTracks, Spotify, Steam, ActivityWatch,
WhatsApp user client, Live listener, Heartbeat, Discord (draft, not deployed;
owner decision pending). This list is the fixed v1 connector set that RFC 0018
anchors to; a connector not named here is deferred, and the deferral
rationale lives in that RFC and the ideas ledger.

### Dashboard

The operator console: butler status, sessions, contacts and identity,
ingestion monitoring, the settings console (health, model catalog, spend,
permissions, owner-confirmed data export and wipe), an append-only audit log,
and signed outbound webhooks with retry. Its role and boundaries are defined
in `docs/frontend/purpose-and-single-pane.md`.

## What v1 Defers

Explicitly out of scope. No v1 work is designed to "prepare for" these at the
cost of v1 simplicity.

- **Multi-user support.** One user, one deployment. No accounts, no tenants.
- **Mobile application.** The dashboard is web-only. No native iOS or Android
  client.
- **Voice as an interface.** No speech-to-text or text-to-speech at the butler
  level. The live-listener connector is transport; in-room voice egress stays
  a gated proposal until adopted.
- **Managed setup.** The Helm chart and compose files are deployment
  artifacts, not an installer. No setup wizard, no one-click deploy.
- **Plugin marketplace.** No third-party module distribution or plugin API
  versioning.
- **Offline reasoning.** State persists locally; reasoning needs LLM access.
- **End-to-end encryption.** The owner owns the database; see
  [security.md](security.md).
- **Multi-LLM orchestration.** One LLM provider per session invocation.

## Platform Targets

Linux (primary) and macOS (development); Python 3.12+; PostgreSQL 15+ with
JSONB; Docker Compose or k3s via the in-repo Helm chart; Claude Code as the
primary LLM runtime with model routing to Codex, Gemini CLI and OpenCode.

## Success Criteria

v1 is complete when:

1. Every staffer and domain butler in `roster/` runs concurrently in one
   deployment and handles its declared responsibilities.
2. The Switchboard routes messages from every active ingress connector to the
   right domain butler with over 90% classification accuracy (lifestyle-only
   ambient connectors such as Steam are excluded from this set).
3. Scheduled tasks fire on their cron cadence and retry transient failures.
4. The memory subsystem stores, retrieves, and consolidates facts across
   sessions.
5. The dashboard shows butler status, sessions, contacts, and ingestion flow
   in real time.
6. The system runs seven consecutive days with no manual intervention beyond
   LLM API key rotation.
7. The owner uses the system daily across at least three domains.
8. Proactive insights arrive at a sustainable cadence without manual tuning,
   and disengagement lowers the rank of ignored categories.

Evidence against these criteria lives in tests, benchmarks
(`tests/benchmarks/`), and Beads, never in this file; a dated status line here
goes stale the day it is written.

## Anti-Patterns

- Building v1 features with multi-user "hooks".
- Deferring reliability work because "it is just v1".
- Expanding connector coverage before existing connectors are solid.
- Adding modules no butler in the roster uses.
- Designing plugin abstractions before the internal module API is stable.
