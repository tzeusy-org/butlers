Models rows retain their existing layout and text Verify action. Add compact capability chips using validated ModelFeature names; absent vision = Unknown, false = Declared unsupported, true = Declared supported. Separate evidence fields show latest check outcome and applied proof applicability. Latest check may be Ready to apply, failed or inconclusive; applied proof may be absent, applicable or stale. A fresh unapplied pass does not hide a stale applied proof or claim restored routing eligibility. Never collapse declaration and proof into a single green check. Historical core248 declarations may show Historical declaration with provenance; no fabricated timestamp or current verified badge.

The existing edit surface exposes non-vision boolean/unknown values with explicit whole-envelope semantics and preserves unedited keys. Vision is not a free true checkbox. Setting true, or preserving true while changing its bound model/runtime/account/config identity, must follow the proof-bound path below. Deliberate Disable vision/Return to unknown are explicit owner actions with normal audit and CAS; they are not automatic consequences of a probe failure. Existing unrelated alias/text/context edits are not blocked by missing proof and cannot manufacture fresh proof applicability.

A visible Verify vision button opens a compact confirmation sheet with exact row alias/model/runtime, environment/account-path display alias (never account identifier or secret), at most three control sessions, enforced token/launch/wall/spend bounds, and whether this run is evidence-only. Default and only v1 run behavior is evidence-only: no automatic capability enablement. Once a standing operation envelope is available, confirming Run vision check starts the one logical operation. This preserves one-click access without hiding provider cost behind an unlabelled action. Missing operational authority shows Not configured for vision checks plus the exact missing category; it does not launch text Verify as fallback.

Operation states: preparing, waiting for authorized capacity, running positive, running text-only control, running removed-image control, passed, failed, inconclusive, cancelled, interrupted. Progress names stages, not content. A failed preflight ends Not run with no charged launch. A successful check produces Ready proof and Enable vision when the row/path still match. A passed run against an already declared-true row says Proof ready to apply and offers Apply proof for a historical unbound row or Refresh applied proof for a managed row. Verify never changes the applied evidence binding, routing eligibility, or declaration, including on already-true rows. Enable vision, Apply proof, and Refresh applied proof are distinct labels for the same explicit audited CAS action using the exact receipt and row snapshot; conflict says Model changed; run a new check and preserves current values.

Busy returns the existing operation status/link for this exact owner/row; second tabs do not launch another run. Navigation/reload reconnects to durable state. Cancellation stops future control launches immediately and requests cancellation of the current session, without promising refund or retroactive effect reversal. A timeout/disconnect is inconclusive unless exact terminal result is already persisted. Stale receipts remain inspectable but cannot enable. Unknown entry gives404; unavailable service gives bounded unavailable state; unsupported runtime reports Not supported by this probe path rather than Model has no vision. No timer auto-runs or Verify all vision fanout.

Focus enters the confirmation sheet, Escape closes before start, Cancel run is explicit after start, focus returns to the initiating row/action; stage/status updates use semantic live status. Buttons remain discoverable with text reasons when disabled. Retry is explicit, preserves previous receipt, and requires a fresh bounded authorization; no background retries. No UI raw output, sentinel, image preview, credential fields or unbounded error text. Ordinary text Verify remains labelled runtime availability, not image support.

## Wire and authority proposal

Owner-authenticated dashboard API is the public administrative surface; use authenticated_principal for actor. Proposed resources beneath /api/settings/models/{id}/vision: GET evidence/status, POST operations (idempotency key + expected row revision + selected preflight authorization identifier), GET operations/{operation_id}, POST operations/{operation_id}/cancel, POST enable (receipt_id + expected row revision). IDs are opaque canonical UUIDs; request models reject unexpected fields and never accept an actor, model prompt, arbitrary URL, image, runtime flags, account identifier, tool list or caller-crafted capability token. Existing API response envelope convention applies. Status/evidence access is owner-only and no broader than model administration.

Preflight uses server-held environment and row/path identity to propose an operation. POST does not itself grant unlimited provider authority. A separately provisioned, explicit owner-approved operational envelope must bind environment, permitted exact catalog row/path, credential-use scope, max3 sessions, max model turns/provider-request count, total input/output tokens, wall deadline and hard spend reservation. Default envelope absent => no call. This contract-adoption question does not supply those values or install keys. Unpriced/unbounded tuple or unenforceable requested caps => not_executable, never a best-effort cost promise. Pricing/account treatment is recorded server-side; subscription zero marginal price is not inferred and call/turn caps still bind.

Private execution capability has a distinct version/purpose/audience from text Verify. Reuse existing audited signing/key/nonce receipt mechanisms only after a paired explicit contract amendment; existing six-claim text tokens are invalid for vision. Capability binds owner-approved authorization ID/digest, operation UUID, environment, catalog UUID, full row snapshot digest, runtime/model/adapter/CLI artifact/version/config digest, opaque account-path fingerprint, synthetic attachment digest and procedure version, exact launch/turn/token/wall/spend envelope, issued/expiry times and nonce. No raw keys/account data/sentinel in claims. Receiver revalidates signature, purpose, deployment audience, all identities/caps and durable replay claim before runtime or attachment effects. Capabilities never enter model context, ordinary tool arguments, session messages or external URLs.

Replay protection is transactional: reserve operation and total budget before launching; one durable launch slot per control; no reusing a consumed slot after an ambiguous crash. In-progress crash becomes interrupted; resuming status never repeats a provider invocation. Late terminal results may close the same slot once, cannot exceed the reservation or produce a second launch. Concurrent same-row operations return conflict/busy; operation and catalog CAS avoid last-writer wins. Expiry prevents new launches, not reading a completed receipt. Budget and cancellation are checked before every provider request/turn, not only session start. If installed CLI cannot expose/enforce those controls sufficiently for a bounded run, tuple stays ineligible until a bounded supported executor exists; do not widen authority to make it run.

## Exact path and controls

Use the production attachment ingestion helper/API contract with generated synthetic PNG bytes, the actual attachment store and attachment_view tool wire output, actual image-intent derivation, actual Spawner and adapter serialization, installed CLI/account path, inference and returned-result parsing. Dedicated probe session contains no owner history, tools beyond the bounded attachment read, shared resume state or cross-operation cache. Transport/policy restrictions are part of the exact evidence identity. Receipt clearly identifies tested restricted probe context; no claim that arbitrary unrelated tools were exercised.

Unknown vision otherwise fails normal fitting. A private typed Spawner entry point accepts only the validated capability and allows its exact candidate to bypass ONLY the unknown/false vision-fit prerequisite for that diagnostic operation. All other enabled-row, runtime availability, auth, quota, timeout, caller/tool/attachment authority constraints remain. No alias fallback, model substitution, other provider, normal caller parameter, temporary vision bit or global configuration. Record the ordinary candidate-fit outcome and the narrowly authorized diagnostic exception in the content-blind receipt. Image intent remains genuine and reaches the ordinary serialization path. Controls use exactly the same tuple/config/account and fresh isolated sessions; only approved attachment delivery differs.

One operation: positive valid image; text-only control with no image delivery; removed-image control after synthetic attachment creation but before attachment_view delivery. No corruption alternative in v1, avoiding inconsistent error paths. Each control receives the same server-owned generic instruction to read the image-only challenge using the one allowed attachment_view request, otherwise return NO_IMAGE; no expected answer supplied. Controls use independent randomized sentinels so an earlier positive output cannot answer a later challenge. Positive must return the exact private comparator value through bounded response parsing; both controls must return NO_IMAGE and never recover their hidden comparator. Every control must issue the exact permitted attachment_view call once and receive its expected typed result before answering. Positive requires the valid image content block; text-only control receives the fixed synthetic no-image result without any image bytes; removed-image control receives the fixed expected unavailable result after authorized synthetic removal. NO_IMAGE without the required call is not a valid negative control. Provider refusal, empty/unparseable output, missing or repeated tool use, unexpected tools, identity drift, leakage, invalid control or unknown termination => failed/inconclusive and no promotion eligibility. No retry/failover/resume. A successful different-model negative control cannot replace same-tuple controls.

The runner creates server-owned source/session/attachment identities independently for each control. The capability binds their exact tuple and the only allowed tool name, attachment ID, fixed argument shape and expected result class for that control. A probe-only attachment authorization filter rejects any alternate attachment/source/session, foreign context, arbitrary URL/filesystem path, extra argument, or tool request before lookup; it cannot rely on the model following the prompt. The same production attachment_view serialization executes after this filter. Control records validate observed exact arguments and result class against that manifest, not caller assertions. Text-only and removed-image control results contain no image and no sentinel. No normal session can claim these identities or this restricted context.

Sentinel exists only in runner-private transient memory and image pixels. Opaque random filenames/IDs; strip image ancillary metadata; no sentinel in prompts, alt text, structuredContent, tool arguments, metadata, receipts, logs, tracing, stdout captures or screenshots. Do not persist a small-sentinel hash. attachment_view must retain image content[] without structuredContent overriding it. Expected control values never cross to the CLI outside positive pixels. Suppress raw provider outputs from session capture for this isolated diagnostic through an explicit reviewed redaction boundary; retain typed verdicts and counts instead. This is not permission to disable ordinary session observability globally. Retained image bytes are access-controlled synthetic artifacts, deleted after comparison/finalization; abandoned artifacts expire through bounded cleanup. Receipt keeps non-sensitive image/procedure digests and cleanup status. Lost comparator after crash => interrupted, no guess/replay.

## Receipt, applicability and promotion

Append-only durable operation receipt: operation/environment/catalog IDs, server actor, procedure version, expected row revision/envelope digest, exact runtime/model/CLI/adapter/config/account-path opaque digests, timestamps, controlled fit exception, per-control launch slot/status/terminal category, enforced caps and accounted usage, positive/negative verdicts, aggregate result, cleanup state and evidence digest. No raw prompt/output/image/sentinel, provider error body, credential/account label or arbitrary metadata. Read model publishes only owner-useful named outcome, timestamps, exact model/runtime version display, caps/usage and applicability reason; internal digests need not fill the UI.

Applicability compares live row/path to receipt on every status/promotion and on image-required routing for rows promoted under this new contract. Exact match plus all three controls passing => eligible for explicit Apply; only a previously applied matching receipt provides managed routing eligibility; identity drift, invalid receipt, missing path provenance or revoked operational procedure => stale/ineligible. Historical declarations without a new proof binding retain existing routing behavior; this migration must not silently remove core248 vision or relabel its probes false. Display historical applicability as not established by this new harness. Converting a historical row to the managed evidence lifecycle requires explicit owner Refresh proof/promote action.

Apply/Refresh locks/rechecks the row and receipt atomically, binds the new managed proof and sets vision=true if needed while preserving unrelated capability keys; already-true values still require this explicit evidence-binding mutation; compare expected complete capability envelope plus relevant row fields/revision to refuse concurrent writes. Repeating the same successful promotion returns the prior result; another row/alias cannot reuse the receipt. No fanout migration/all-alias update. Deleting/disabling/changing identity invalidates a new pending promotion. No lost update through existing whole-envelope PUT: enabling managed vision must route through receipt validation, and updating a managed row's runtime/model/config invalidates managed eligibility in the same transaction. Standard unrelated edits retain proof if exact path is unchanged. Managed stale proof excludes image-required selection even if historical declaration field remains true; metadata explicitly differentiates that managed gate from legacy evidence. This new routing applicability behavior requires explicit spec adoption; do not silently retrofit it under existing API validation.

## Specification scenarios for review

1. WHEN Models loads declared true/false/absent and legacy/new evidence rows THEN declaration and applicable-proof states are distinct, with no raw true checkbox.
2. WHEN ordinary Verify succeeds THEN vision evidence and capabilities are unchanged.
3. WHEN an owner confirms an executable bounded vision operation THEN exactly one purpose-bound operation is created and real production attachment/intent/Spawner/adapter paths execute under its exact tuple.
4. WHEN authority, caps, required signing material or exact identity is missing THEN no provider session starts and UI reports Not run with bounded reason.
5. WHEN an ordinary session or text-probe token attempts diagnostic bypass THEN it is denied before side effects and normal unknown-vision routing still fails closed.
6. WHEN positive and both same-tuple negative controls finish with valid verdicts THEN Ready to apply evidence is recorded without changing vision, applied proof binding or routing eligibility, including for an already-true row.
7. WHEN sentinel reaches any forbidden channel, control is ambiguous, timeout/cancel/crash or identity mismatch occurs THEN no promotable pass exists, no automatic retry launches and previous declarations remain untouched.
8. WHEN duplicate request/reload/concurrent tab uses the operation THEN no second launch slot or budget is consumed and status resumes durably.
9. WHEN owner enables or explicitly applies/refreshes a matching completed proof THEN CAS binds that receipt and merges vision=true only into that exact unchanged row; stale/concurrent/other-row requests fail without lost updates.
10. WHEN a managed-proof row path changes THEN status becomes stale and image-required fitting refuses it until a new matching proof; historical unbound declarations are not silently rewritten.
11. WHEN Models status, confirmation and completion are operated by keyboard THEN focus and live announcements remain usable, reasons are readable and no raw proof content leaks.
12. WHEN this feature is disabled/rolled back THEN no pending operation may launch, receipts remain durable, managed rows do not fall back to unproven vision eligibility and ordinary text verification remains available. Code downgrade requires compatible fail-closed managed-evidence handling; no silent dropping of its gate.

No revision numbers reserved. New core migration must work on core-only databases, replay per schema safely, and preserve existing public.model_catalog and text-probe contracts. Use PostgreSQL row locks plus canonical digest of all relevant row fields/envelope for expected-revision CAS; do not pretend current model_catalog already has a dedicated monotonic revision. Existing updated_at is part of evidence but alone is insufficient full-envelope/path equality. Representation fields below are proposed names, subject only to semantics-preserving engineering naming review.

A unique in-flight catalog key serializes concurrent operations; idempotency identity binds principal/catalog/request digest, not arbitrary reuse across a changed request. Persist no raw capability token or credentials.

public.model_vision_control_receipts: operation+control ordinal unique, control enum positive/text_only/removed_image; allocated/started/terminal slot state and times; synthetic source/session/storage-ref digest and expected tool/result-manifest digest; usage/counters; bounded typed verdict. The manifest's raw synthetic refs are private executor inputs, never a new arbitrary attachment permission. Slot reserve commits before launch; ambiguous started remains consumed. Durable per-request admission accounting checks total envelope before each provider request, not just sessions. Missing CLI enforcement yields not_executable.

public.model_vision_applications: catalog UUID unique, receipt/operation reference, applied expected/live path digest, applied timestamp, server actor, applicability generation. Apply locks row+eligible receipt; verifies all controls, unconsumed or idempotently same application, exact path and snapshot; merges only vision=true plus application binding atomically. A historical row has no application record. Reads of a latest successful operation do not touch applications. Deletion cascade/retention must preserve audit receipts without reviving a row; keep tombstoned catalog identity in receipt, never rebind by alias.

State writes belong only to authenticated private control/server-owned catalog application procedures. Runtime role privileges and forced RLS/owner-bypass fences must follow core201/core212 precedents with real bootstrap replay; no blanket public runtime DML or client-selected SECURITY DEFINER table/name. Maintain schema-owner separation; exact current roles and migration ownership verified before code. Error categories fixed. No endpoints accept actor, arbitrary prompt/image/url/tool/model override or caller-generated capability.

Models non-vision edits retain whole-envelope replacement and validation; preserve untouched fields. Every path that writes a new vision=true value, including new, cloned, unbound and imported rows, or preserves true while changing relevant identity (including historical true rows) must verify/invalidate binding atomically, including bulk/import/admin mutation paths found in source inventory; no protection only on new endpoint. Historical unbound values remain as they were until explicit Apply/Refresh. Clear/disable actions are explicit owner CAS, never automatic probe failure handling. Preview estimated caps is not proof enforcement or live spend authority.

# Restricted dispatch and durable storage authority

## From dashboard admission to exactly one control session

Existing ingest_v1 performs policy checks plus message_inbox and ingestion_events persistence; it does not itself prove constrained execution. Its pinned target shortcut bypasses policy evaluation, and policy_evaluator=None skips annotation: neither is acceptable as the diagnostic safety boundary. Introduce a typed PRIVATE diagnostic-admission path sharing production envelope validation/attachment normalization/storage and required ingress-policy evaluation, with an immutable server-authorized operation/control owner. The dashboard never submits these fields or an arbitrary routing target. Rejected/quarantined/policy-held ingress means Not run; do not disable evaluator to get a pass.

Persist the synthetic ingestion event and an explicit diagnostic ownership/lifecycle marker atomically with control-slot reservation. Add corresponding CHECK/state support through a reviewed migration. No ordinary accepted message_inbox work item may be published for this event. Every ordinary classification/triage fallback, inbox poll/recovery, observer fanout and route delivery consumer must exclude diagnostic-owned events by its authoritative predicate; inspect ALL producers/consumers, not only the API branch. Diagnostic owner is Switchboard private control coordinator; target is fixed isolated probe execution context plus the signed exact catalog tuple, never an LLM-classified butler. It claims the slot and passes stored event attachment descriptors through the real Spawner diagnostic entry and actual derive_dispatch_intent. No classification session, summary job, observer or opportunistic retry may launch beside the three authorized sessions. Policy evaluator required, no prompt route request, no policy_evaluator=None. Test persisted event restart/recovery with normal consumers running and planted positive ordinary controls: diagnostic event launches once only through owner; normal event still dispatches. Counters include every provider launch and request, not just visible result sessions.

## Exact DB principals

Reuse existing runtime principal butler_switchboard_rw for private execution ledger access with ENABLE+FORCE RLS USING/WITH CHECK current_user = butler_switchboard_rw. Neither ordinary QA/other butler roles nor role=none migration/audit pool may read/write. Shared login may SET ROLE only through reviewed existing authority; it is not itself an allow condition. Tables owned by migration owner remain fenced under FORCE; revoke PUBLIC and runtime broad grants, test init-db replay. TRUNCATE is denied by explicit trigger in addition to privilege/RLS (RLS alone does not cover it). Immutable terminal receipts reject UPDATE/DELETE; controlled state transitions validate prior state and allowed field changes. Application procedure fixed table/columns, no caller SQL/role/name, verifies active role, actor from authenticated API/signed private request and exact row/path snapshot.

Owner dashboard status/read/apply/cancel calls use a separate purpose-bound private control RPC; they do NOT open roleless direct table SQL. The service validates authenticated owner caller capability before using its own role-scoped DB pool. Status requests cannot acquire execution authority. Pool acquisition scopes SET LOCAL ROLE in transaction and resets on success/error/cancellation; tests execute real roles, forged caller/purpose and owner/no-role bypass. Fixed projections contain no raw sentinel/provider output. Do not grant dashboard or generic runtime pool table privileges merely to simplify routes.

## Backup, restore, retention and replay

These three NEW ledgers are durable proof/control records, not core201/core212 short-lived five-second nonce data. Do not add them to its backup exclusion list. Backup exports their complete consistent snapshot through an explicit narrow butler_switchboard_rw read role invocation (separate from normal migration-login dump) and includes schema/policies/triggers plus sidecar receipt in restore manifest. Existing backup architecture must review exact role/restore integration; no backup runtime changes are executed here. Restore imports through a fixed validated import procedure under the same role, not disabling forced RLS or TRUNCATE fences.

Never expire an applied proof or consumed operation replay tombstone merely because its signing token expired. V1 retains terminal content-blind receipts/application history/replay identities indefinitely; no age-based purge is introduced. Synthetic image objects alone expire after comparison or interruption cleanup, with cleanup receipt. If storage growth later requires a retention policy, that is a distinct reviewed data-policy amendment. Restore is fail-closed: generate a new deployment/executor epoch, stop launch admission until all restored in-flight slots are terminal interrupted and capabilities from previous epoch are invalid. Restored terminal spent slots stay consumed. Applied proofs tied to old environment epoch become stale until a new exact proof and explicit application; no automatic historical rewrite. Restoring an older backup must not accept unexpired capabilities created after that snapshot: mandatory epoch rotation before startup, not reliance on receipts absent from backup. A rollback cannot drop the managed-routing fence or ledger while readers exist. Disposable full backup/restore tests must prove schema+data recovery, forged replay rejection, no duplicate launch and new-epoch activation separation.

## Restore epoch implementation contract and owning paths

The fresh executor epoch is generated by a host/control startup fence OUTSIDE restored database/backup contents. Never recover the active epoch from a restored row, configuration snapshot or receipt. The control service MUST refuse every read-to-execute transition and issued capability until restore status and fresh epoch are installed, all restored running slots marked interrupted, and old-epoch authorities invalidated. Every issued vision capability includes this epoch in its signed exact payload; every private receiver checks equality to the active host epoch BEFORE nonce claim, attachment access or provider effects. Each applied proof path digest includes that epoch; old epoch therefore cannot authorize managed image dispatch. Status/backup reads remain read-only while fenced. Startup/restore failures fail closed; ordinary text probe tokens do not gain this field or authority implicitly. No current implementation is claimed.

Owned implementation/documentation map: deploy/backup/pg_dump.sh (include durable ledger export in same consistent shared snapshot, manifest and checksums), scripts/pg_restore.sh (fixed validated data restore and pre-service epoch fence), scripts/pg_verify_restore.sh (required ledger/schema/trigger/epoch readiness evidence), src/butlers/core/runtime_probe_control/activation.py and new purpose-specific capability/endpoint (issue/check/startup block), deployment control configuration templates only, docs/operations/backup-restore.md and docs/runtime/model-routing.md. Reuse established cost-claim scoped shared-snapshot/export architecture; do NOT invent unrelated dump transactions for each ledger.

Nearest tests: tests/scripts/test_pg_dump_backup.py; tests/scripts/test_pg_restore_definer_ownership.py (existing cost-claim role-scoped shared-snapshot pattern); tests/scripts/test_restore_drill_evidence_backup.py; tests/core/test_runtime_probe_control_activation_guard.py; tests/core/test_runtime_probe_control_capability.py; tests/api/test_runtime_probe_control_receipts_db.py. Extend real disposable backup/restore outcomes, plus exact epoch forgery/replay/startup failure cases, not source-grep or separate repeated whole-database gates. operation_authority owns these backup/restore source changes and serializes with any current backup/restore owner; no unallocated follow-up.
