# Nightly assurance proposal (Released source implementation; delivery evidence pending)

## ADDED Requirements

### Requirement: Complete nightly evidence preserves assurance
The nightly workflow SHALL retain both future-date offsets, full selected Python/roster population, schema/migration and all four exact-image kernel proofs, and assess each result using complete same-run identity-bound privacy-safe evidence. UNKNOWN SHALL remain non-green.

ID: REQ-nightly-ci-assurance-001
Source: bu-ly3lv5.2 complete original clauses; testing-and-verification; protocol P1–P12 and verification V1–V8
Scope: v1-mandatory

#### Scenario: Whole corpus and distinct clock species
- **WHEN** a normal nightly is selected
- **THEN** both45d and120d, default nightly and four exact-image proofs retain their complete existing population and phase contracts

#### Scenario: Receipt identity and privacy
- **WHEN** variant evidence is collected
- **THEN** run/attempt/SHA/command/manifest/exit bind sanitized JUnit; raw failures/parameter values/provider text are never exported

#### Scenario: Missing or incomplete execution
- **WHEN** a variant/manifest/finalizer/receipt is missing or killed
- **THEN** assessment is UNKNOWN with partial reached failures retained, never PASS

#### Scenario: Session and item bounds survive
- **WHEN** a test or finalizer hangs
- **THEN** default300 and owning75m/3600sABRT+30sKILL bounds remain nonpassing and diagnosable

#### Scenario: No quarantine or speculative selector
- **WHEN** someone proposes narrowing or moving a check
- **THEN** the exact survivor/transitive coverage proof is required and full merge_group assurance stays unchanged

### Requirement: Second-red incidents are authoritative owned work
The automation SHALL reconcile a second adjacent scheduled red night to one workflow-plus-failing-set incident Bead, actual node-owner mapping and a real notify-boundary attention row through the existing trusted host coordinator and Switchboard operational boundaries. GitHub issues SHALL be evidence transport only, and unknown acknowledgements SHALL not create duplicate work or fictional delivery.

#### Scenario: Two real nights and attempt replacement
- **WHEN** two adjacent scheduled UTC dates have verified failure
- **THEN** the current canonical failing set keys one incident; same-night retries never increase the streak

#### Scenario: First red and incomplete evidence
- **WHEN** one night fails or later evidence is missing/cancelled
- **THEN** triage/UNKNOWN remain visible without claiming two verified red nights or recovery

#### Scenario: Dedupe and changing failure sets
- **WHEN** the same workflow/set repeats or a second-red set changes
- **THEN** same set reuses its incident; changed sets have explicit separate keys with no one-Bead-per-night duplication

#### Scenario: Actual host tracker admission
- **WHEN** a versioned issue receipt reaches the reconciler
- **THEN** host independently verifies repository/workflow/run/attempt/head then the sole coordinator uses its existing bd identity and independently reads back one incident and owner map

#### Scenario: Crash and recurrence
- **WHEN** acknowledgement is lost after creation or a recovered set returns
- **THEN** external_ref readback precedes create and recurrence reuses the incident with a new episode

#### Scenario: Attention path and scope
- **WHEN** a verified incident export is observed by the registered Switchboard job
- **THEN** current policy/recipient/delivery primitives produce a real ledger decision with existing outcome semantics and no fabricated delivered/failed/uncertain classification

#### Scenario: Ledger loss and ambiguous delivery
- **WHEN** ledger persistence fails after known delivery or transport acknowledgement is unknown
- **THEN** only ledger persistence may retry for known delivery; ambiguity retains pending uncertainty and never resends automatically

#### Scenario: Recovery and adoption availability
- **WHEN** all required variants recover or the coordinator/export/job is unavailable
- **THEN** complete green closes escalation only; unavailable automation remains visible and cannot satisfy the original Bead/attention outcome

### Requirement: Nightly red backlog has causal fixes and owners
Every actual selected failing node SHALL have an owned Bead and source-bound cause/evidence; clock and PostgreSQL corrections SHALL preserve data, authority, lifetime, privacy and positive controls rather than weakening the selected checks. Historical dossier totals SHALL not masquerade as current measured counts.
