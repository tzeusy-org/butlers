# Generalist lead with focused depth-one delegation

**Status:** Owner-adopted project shape and capability reservation (2026-10-14);
not an implementation-ready contract or runtime activation.
**Tracking:** `bu-rn8frx` (shape adoption); `bu-7p9ll5` (successor design).

## Why

Domain ownership is valuable, but mandatory specialist reasoning for each domain
conflates durable responsibility with model context. The owner requested a
future architecture that handles whole cross-domain goals with a generalist
lead, discoverable capabilities, and focused children with dedicated prompts.
The [doctrine amendment](../../../about/legends-and-lore/decisions/2026-10-14-doctrine-focused-delegation.md)
records evidence, tradeoffs, current guarantees and downstream impacts.

## What Changes

- Reserve a goal-orchestration capability: one accountable lead per goal,
  optional children at depth one, explicit task briefs and inherited policy.
- Preserve domain custody, proactive obligations, MCP capability ownership,
  approval gates and finite work budgets independently of reasoning topology.
- Require runtime-enforced lineage and authority, coherent final outcomes,
  cancellation propagation, and recovery without budget resets or effect replay.
- Keep current contracts in force pending an explicit successor RFC, baseline
  deltas, implementation and activation evidence.

## Capabilities

### New Capabilities

- `goal-orchestration`: Bounded generalist-led reasoning across domain-owned
  capabilities, including focused delegation and durable accountability.

### Modified Capabilities

None in this shape reservation. It cannot be implemented or archived as a substitute
for modifying conflicting baseline requirements. Follow-on design must amend
`butler-base-spec`, `core-spawner`, `core-daemon`, `core-sessions`, `core-modules`,
`butler-switchboard`, `cross-butler-delegation` and any chosen host role contract.
The decision record inventories further affected artifacts and active changes.

## Impact

This change contains documentation and reserved target scenarios only. It does not
select the hosting daemon, alter a roster manifesto, widen live tool access,
introduce generic invocation tools, require a provider change, or ship code mode.
The current v1 scope is preserved; `v1-reserved` records a design reservation,
not release admission. Runtime implementation needs its own approved scope and
exact wire, authorization and lifecycle design before work is dispatched.
