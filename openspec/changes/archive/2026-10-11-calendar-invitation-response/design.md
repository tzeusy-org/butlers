## Existing-source compatibility

The current gate parks unresolvable targets and applies standing rules only to resolved contact identities. Response executable arguments contain no channel/recipient/entity target and cannot acquire an outbound-owner exemption. Future trusted preparation is a registered module-owned callback, not caller metadata or a raw handler call. Its immutable command and pending action commit on one owning connection; current park_pending_action accepts an existing connection through _connection and nested transaction semantics, while current Calendar _prepare_workspace_mutation remains read-then-record and is not the new atomic claim.

Current approve_approval verifies the request principal, sets create_rule=false, audits the decision transaction and then calls _dispatch_approved_action_outcome for the actual owning daemon. The future response service must preserve these exact checks and prove same action/tool/digest, not call a route with fabricated Request state. execute_approved_action owns task-bound approved lineage and durable eligibility; a separately committed Calendar egress start must survive a shared-executor transaction rollback.

The existing Google OAuth and Rate Limiting requirement retains its ordinary retry scenarios and all other tools retain their behavior. The dedicated response write is a narrower new operation: readiness/token refresh precedes the durable claim, then exactly one conditional participant write with no transport/application write retry. Approval retry eligibility remains governed by module-approvals; the Calendar unresolved-start fence makes repeated dispatcher invocations perform zero second provider writes.

The existing event-home resolver's primary fallback, flattened attendee update and old-tool inverse exception release are not response admission/uncertainty mechanisms. No existing CRUD, recurrence, radar, invitation provenance, read default, undo scenario or approval recovery surface is changed by this active contract.

## 1. Trusted target preparation before parking

The public calendar_respond invocation accepts entry_id, response_status in
accepted/declined/tentative, request_id, and send_updates in none/all/externalOnly
(default none); the existing undo route can request a server-owned inverse
reference. It does not accept actor, owner_click, bypass, caller approval id,
caller target/account/calendar/ETag, or a caller-installed command binding.
Dossier metadata remains validated by the existing gate. The HTTP owner path
uses a deterministic truthful dossier and the existing authenticated principal.

Add a trusted module-owned, Calendar-specific canonical-preparation callback to
the actual gate composition, invoked after public argument validation and before
target resolution/rule matching/persistence. This callback is registered from the
actual Calendar module object at startup, never serialized in request metadata.
The original handler is not invoked for preparation. It resolves the projection
entry to its exact operational owner, source/account/calendar/provider-event and
actual occurrence; verifies source eligibility and current provider event by
read; verifies the configured Google account or an independently verified primary
account and exactly one matching self attendee; freezes pre-state and ETag.
Provider self=true denotes the event copy's calendar, not proof of account
identity. config.account/account-registry identity and the credential/source
binding must agree; missing or conflicting primary proof refuses.

Do not use _resolve_home_calendar_id's final primary fallback. The dated original
name _resolve_calendar_id_for_existing_event is not an installed symbol. Reject
cross-source UUID ambiguity, absent/degraded owner lookup, changed source identity,
cancelled/removed/ineligible/read-only source, invalid status, missing/ambiguous
self, organizer-only entry or recurring series root. Recurring instances bind
provider instance id, recurringEventId and originalStartTime; no series expansion.

Preparation persists an immutable, versioned command in the existing owning
calendar_action_log JSONB payload, with exact request key, owner/target/self,
prior status, requested status, send_updates and ETag. An atomic unique insert
and locked full-digest comparison select one command. The prepared command and
its actual pending action bind and commit through one owning connection with
the current park_pending_action transaction interface, including the existing
default-off/enabled delivery-admission obligations. Failure rolls both back.
No new table/grant or peer SQL is needed. This is new implementation work: the
current read-then-record _prepare_workspace_mutation is not that claim.

Parked executable kwargs contain the explicit public command values and trusted
command id/digest binding accepted by the original registered handler. The actual
registered public schema rejects caller injection of internal bindings; the
preparer installs them privately and the replay handler accepts exactly that
shape. Startup validates the original handler signature, callback, Calendar
write metadata, enabled tool group, actual gate and same-owning-daemon executor.
No new MCP name, alias or hidden raw-handler API bypass is introduced. Exact
FunctionTool registration/schema/interception tests must prove this composition.

Executable args carry no entity_id/channel/recipient/chat_id/to/chat_jid. Current
_extract_channel_identity therefore remains unresolved; self response is not an
outbound owner-recipient exemption. Neither a forged recipient field nor a broad
standing rule can execute it: unknown args refuse and actual unresolvable-target
gate behavior parks. Preserve all existing other-tool owner/standing-rule policy.
Pin every command binding as safety-critical and require exact same-task/tool/
argument approved context at the original handler, plus the owning durable
command/pending-id relationship. A inherited child context is insufficient.

## 2. Verified dashboard decision uses the actual approval service

POST /api/calendar/workspace/respond resolves the entry from authenticated
server-side ownership, calls the actual owning registered gated calendar_respond
tool, and receives its exact pending id/command binding. The server checks that
row in that same owning schema, with the exact tool and materialized digest;
it then uses a factored shared service containing the current approve_approval
verified decision/audit and _dispatch_approved_action_outcome path. create_rule
is false, edits are absent, no caller approval id is accepted, and no raw original
handler is called. The existing HTTP request principal remains the authority;
X-Butlers-Decision-Actor is accepted only through its current verifier, not copied
from raw input. Expired/rejected/wrong owner/changed digest refuses before effect.
A disconnect never converts approval acceptance into provider completion.

Autonomous calls without the exact decision park; a verified click is one
approval act, not standing consent. The same action id/digest is used in review,
dispatch and receipt. Replay loads the existing command and action rather than
creating an extra pending command. An expired/rejected command cannot be reissued
under the same key; a genuinely new request must re-prepare and require approval.

## 3. One provider write attempt and honest outcome

Before network dispatch the original handler rechecks approved context, live
source capability, current exact provider event and frozen ETag. Same status is
noop without write or usable inverse. Refresh OAuth/readiness before the write
claim. Commit egress_started in the owning action log on a separate own-pool
connection before the HTTP write, so the shared approval executor's transaction
rollback cannot erase a possible external effect. One atomic transition wins;
duplicates reuse or report existing pending/uncertain/applied/noop outcome.

Use a dedicated Google participant-response operation: a single conditional
PATCH with If-Match, attendeesOmitted=true and only the verified self participant
email/responseStatus, plus the bound sendUpdates value. Preserve organizer, other
attendees, title/time and recurrence. Do not use update_event's flattened attendee
replacement or generic _request_with_bearer write retry: current 401 and 503
paths can issue another write. No HTTP transport/application retry is enabled for
this dedicated write. Existing operations retain their current behavior.

Known explicit provider rejection (including 412) yields a failure attempt audit,
no applied receipt or inverse, and authoritative projection/needsAction remains
honest. Cancellation, disconnect, restart, timeout or connection loss after a
durable start leaves the exact command uncertain; approval remains retryable by
its existing lifecycle, but every repeated executor call encounters the durable
Calendar fence and performs zero second writes. A new request key must not evade
an unresolved started command for the same source/occurrence. No elapsed TTL,
new worker lease, read-only match or guessed provider status clears this fence.
Post-start reconciliation may record provider current truth separately; matching
status/ETag alone cannot attribute that change to this command and grant an
applied receipt or undo. Verified late result from the original attempt can
resolve its own command. Missing safe provider evidence stays uncertain.

Only a verified response from the own write confirming the exact target/self
and expected change earns applied receipt. If subsequent projection persistence
fails, keep that provider receipt with projection_available=false; do not call it
a rollback or resend. A tool-level error/unsuccessful result on uncertainty must
prevent the shared executor from marking the approval executed; applied plus
projection-unavailable may return a successful recorded provider outcome.
No provider exception strings, URLs, tokens or event bodies enter logs or public
error categories. Existing privacy/redaction applies to the owner-bound dossier.

## 4. Guarded inverse on the existing endpoint and same tool

The actual baseline title is Calendar Mutation Undo Endpoint. Preserve every
whole old requirement clause and eight old scenarios for create/update/delete,
including the no-new-undo-MCP constraint. Add workspace_user_respond handling to
POST /api/calendar/workspace/undo/{action_id}, invoking the same calendar_respond
with a server-owned inverse reference and fresh request_id. An inverse restores
only the recorded prior self response, including needsAction, never flattened
attendees or event fields. Ordinary respond cannot submit needsAction.

Resolve exact action owner without cross-pool first-match ambiguity, verify an
applied original with retained pre-state, exact self/account/source/instance and
post-status/post-ETag, and no intervening update. A locked single-use inverse
claim binds the new approved inverse command. Concurrent or repeated undo refuses
or reuses the one pending inverse; no second egress. Unknown/failed/noop original,
missing/expired pre-state, stale or changed provider source refuses. Existing
receipt retention governs; no invented undo duration. Pre-start refusal may
release only a provably non-started claim; started uncertainty retains the fence.
Do not apply the existing old-tool generic exception release path to an uncertain
response inverse. All old-tool inverse behavior remains unchanged.

## 5. Capability, lifecycle, UI and rollback

Current Calendar core-tool owners general/health/lifestyle/messenger/relationship/travel
are an inventory, not six enabled response capabilities. Only messenger and
relationship currently load approvals and neither installs calendar_respond.
Future source-only per-owner roster installation must name actual Calendar,
approvals, registered preparer/original tool, gated entry, shared executor and
existing Google source/account eligibility. Missing any component disables/refuses
the tool and API effect. Do not reroute a General-owned entry to Messenger to
borrow its approvals. No live installation, new scopes or credentials is released.

The new operation uses current provider client timeouts and existing request/
daemon shutdown ownership, not unbounded detached tasks. Cancellation after start
records uncertainty; before start records no effect. Durable replay and unresolved
fences survive restart without a polling resend loop. Existing receipt retention
must not prune unresolved start/fence records or let pruning re-admit a possibly
started command; safe compacted non-reacceptance records remain in existing own
action-log storage where necessary. This required mechanism must be tested before
delivery, not inferred from an absent current retention job.

Palette, contextual and keyboard Accept/Decline/Tentative all call one typed
handler. Pending appears immediately and remains while an approval/dispatch is
outstanding; double click reuses the request key. No optimistic accepted badge,
invitation removal or enabled undo precedes authoritative provider truth. Show
rejection, blocked/missing capability, uncertainty, degraded projection, review
door and applied receipt distinctly; preserve focus, accessible names, existing
permissions and loading/partial/clean-empty honesty. Receipt/current provider state
are different facts. A stale response cannot update a replacement source/entry.

Rollback disables the new source registration/route/verbs and preserves all
commands, pending decisions, audits and unresolved fences. A compensating undo
is still consequential and needs the same approval. RFC0023 notification recovery
remains notification-only, dormant/default-off; this feature neither activates
its transport nor borrows its private same-PID credential/issuer authority.
