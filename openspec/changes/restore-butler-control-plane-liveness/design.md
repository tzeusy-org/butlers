## Context

See [proposal.md](proposal.md) and the [2026-09-23 reliability review](../../../docs/reviews/2026-09-23-liveness-control-plane-reliability-packet.md). Currently `background.py` sends unauthenticated heartbeat POSTs to an owner-protected Dashboard endpoint; the registry expires and routing refuses every stale target. Scheduler dispatch consults that same registry and disables QA patrol. The launcher accepts process `/health`, which cannot detect the routing failure. Startup registration and heartbeat also share `quarantined` fields with operator policy.

The selected deployment is one trusted host with exact Git-roster endpoints on the internal backend network. No additional process-bound signing key is adopted. A future untrusted-host topology requires a separate security-doctrine amendment. Connector heartbeats and their liveness model are independent and unchanged.

## Goals / Non-Goals

**Goals:** receiver-owned liveness and generation fencing; independent local scheduling and fleet observation; owner policy persistence; semantic deployment readiness; content-blind correlated incident evidence.

**Non-Goals:** changing connector heartbeat authority; making heartbeat POST public; adding a service secret; automatic historical ingestion replay; external monitor provisioning or public synthetic route execution.

## Decisions

### 1. Probe an exact daemon endpoint and record the receiver's time

Extend the daemon's same-port internal HTTP app beside `/health` and `/mcp` with `GET /internal/control-plane/identity`. It is reachable only on the trusted backend network and is never an MCP/model tool. It returns bounded JSON:

```json
{
  "schema_version": "butler.control.v1",
  "butler_name": "<Git roster name>",
  "boot_instance_id": "<UUIDv7 generated once per process start>",
  "boot_epoch": 42,
  "route_contract": {"min": 1, "max": 1},
  "accepting_routes": true
}
```

The daemon generates a boot UUID once per process and binds its configured port before advertising route acceptance. A narrowly granted database registration, bound to its effective runtime role and Git-derived roster name/endpoint, allocates and durably returns a strictly increasing `boot_epoch` for that daemon. A repeated call for the same UUID returns its original epoch without changing the current epoch; an older boot cannot renew itself after a successor registers. The daemon reports `accepting_routes=false` until registration commits, and then exposes both UUID and epoch in the identity response. The registration is process succession evidence only; it does not write a healthy observation or administrative policy.

The observer constructs `host:port` from exact Git roster config, never a registry value or caller parameter. It enforces request deadline, response size/schema, name equality, supported route-contract intersection, and acceptance. The response carries no liveness timestamp, private endpoint, credential, or owner data. On shutdown or pre-accept startup, `accepting_routes=false` is truthful. Registered port must match the configured endpoint, but the response does not authorize a port change.

The Dashboard/control-plane lifespan supervisor owns periodic probing with bounded fanout and a single-flight probe per daemon. Switchboard owns only the one on-demand recheck of an otherwise eligible stale route. Both processes use the same exact-roster verifier and database functions to reserve a per-daemon probe sequence before network I/O and conditionally record the result afterward. The record operation requires both the latest durable `boot_epoch` and a current reserved sequence; a larger probe sequence from an old epoch still fails. The database stamps `observed_at` itself. Reserve/record functions are granted only to the two control-plane runtime roles, check roster-bound names and endpoints, and cannot change policy; neither process receives dashboard owner-auth authority. A response deadline and total route deadline bound the on-demand call. Database and controller failures yield `observer_unknown` or `unavailable` evidence, never a fabricated healthy renewal. Confirmed route success remains secondary evidence and cannot override identity, epoch, or policy.

Alternative rejected: accepting daemon POSTs under an anonymous exception or distributing owner credentials. Both expand authority through the protected Dashboard API. A new signed daemon credential would also require a separate doctrine adoption and operational rotation.

### 2. Store independent observation, policy, and compatibility

Expand the Switchboard registry with a durable latest-boot record (`boot_instance_id`, `boot_epoch`), an observation record (`state`, latest `observed_at` attempt, separate last verified healthy `healthy_observed_at`, `observed_boot_epoch`, `observer_sequence`, bounded failure class), policy record (`active|paused|quarantined|review_required`, actor, changed time, reason category), and compatibility record (contract intersection and acceptance). A failed probe advances the attempt time and failure state, never the last healthy time. The System Overview's legacy `last_heartbeat_at`/age projects only `healthy_observed_at`, adds `last_probe_at` for attempt time, and derives row status from observation and policy rather than age alone. The old `eligibility_state` becomes a derived read projection during migration and can be removed only after all readers move. Effective eligibility requires all three dimensions and exact equality between observed and latest registered boot epochs. Every writer is audited for authority: daemon boot registration advances only the latest epoch; Dashboard and Switchboard probes write observation/compatibility through fixed functions; owner API writes policy; route success supplies bounded secondary positive evidence; the old heartbeat POST writes none.

The existing `quarantined_at` and metadata cannot prove all legacy rows' provenance. A pre-cutover migration classifies rows using operator audit and automatic TTL sweep events. Proven automatic expiry becomes observation; proven operator action becomes policy; undecidable rows become `review_required`. Preserve the old row and classification evidence in a migration receipt. Do not make policy sticky until this classification is complete. Rollback restores the old read projection while retaining restrictive policy and provenance, never broadening a target's eligibility.

Alternative rejected: treating every existing quarantine as owner policy. The TTL sweep also created these rows, so that would freeze automatically expired daemons indefinitely. Treating every row as automatic would silently clear genuine owner intent.

### 3. Recheck stale routing once and leave local schedules running

When a target is stale and all non-health gates pass, Switchboard reserves its own DB sequence and performs one on-demand probe to the exact Git-roster endpoint using the shared verifier. It never calls Dashboard or inherits its owner-auth boundary. A valid latest-epoch response conditionally recorded before the route deadline permits one route attempt. Probe, DB admission, or CAS failure returns the existing canonical transport envelope `outcome=not_attempted` with a typed transient target-unavailable reason, and calls no target. Administrative policy and compatibility denials do not enter the stale recheck path. Reuse the shipped `confirmed|rejected|uncertain|not_attempted` vocabulary; the legacy top-level `retryable` flag is not the certainty authority.

The scheduler's local cron/deadline decision checks explicit administrative policy only. It does not use derived remote registry staleness as a reason to suppress work. This includes QA patrol and Switchboard eligibility sweep. Scheduling and inbound routability therefore have distinct controls. A successful registry read that says `stale` is evidence for inbound routing, not a local stop signal.

Alternative rejected: restarting every daemon after expiry. Startup registration can briefly make rows look fresh but cannot repair a rejected heartbeat or prove sustained health.

### 4. Observe QA and correlate fleet failure outside QA

The Dashboard/control-plane supervisor schedules fleet reconciliation and QA patrol-age checks independently of QA's own scheduler. Its expected set comes from the Git roster. A complete snapshot may resolve a condition; failed or partial snapshots may add evidence only, following the active infrastructure reliability lifecycle. A common observer/control failure is one condition identity with an affected-daemon set in evidence, not one identity per daemon. At cutover the QA `infra_state` source in the active `durable-dashboard-terminal-action-recovery` change reads that condition instead of deriving per-butler failures from old `last_seen_at`/`quarantined_at`. Existing per-butler condition episodes remain linked and historically readable, but do not page or dispatch duplicate investigations; they resolve only after a complete receiver-observed snapshot proves that specific daemon recovered. QA discovery persists even if LLM/GitHub dispatch is unavailable.

The QA staffer manifesto must list all five shipped discovery sources and remove its legacy direct-self-healing fallback; RFC 0015 already centralizes investigation. Initial patrol-overdue threshold is twice configured cadence, with a content-blind distinction for an intentional administrative stop. A genuine completed `suppressed` cycle is healthy discovery when novel findings were filtered by cooldown/severity; the dashboard's synthetic validation placeholder also uses `suppressed` but ran no sources. Add nullable provenance fields to `public.qa_patrols` for `origin`, enabled-source snapshot/config digest, and explicit discovery completion. The scheduled QA writer captures the enabled set at start and marks completion only when all enabled sources succeed; the synthetic writer sets its own origin and incomplete marker. Legacy rows remain unknown, never inferred healthy from status or free-text error detail. Only completed scheduled `clean`, `findings_dispatched`, or genuine `suppressed` patrols with all-source success under the current enabled-source configuration renew freshness. `running`, `error`, `skipped_overlap`, synthetic `suppressed`, failed-source, and ambiguous legacy rows do not. Condition identity uses versioned stable source facts and the existing complete-snapshot lifecycle.

### 4.1 Deliver one durable owner attention episode per condition

The independent control-plane supervisor is also the fixed producer for `fleet_control` and `qa_patrol_overdue` owner attention. Its producer-owned initial grace and controller cadence must place the first durable attention intent no later than ten minutes after a recognized fleet failure or overdue QA patrol while the database and controller are available. The producer uses the existing condition episode UUID as the immutable edge key. It does not invoke QA or Messenger, inspect event content, or render a transport message. A narrow `SECURITY DEFINER` append operation verifies that the named condition episode is active, belongs to an allowlisted source, and has crossed its first attention threshold; it derives source and fixed safe payload on the server. The observer role receives execute permission only, no raw outbox DML or owner credential. A partial unique key on condition episode UUID ensures concurrent scans, restarts, and repeated L1 checks return one outbox row.

The current `runtime_attention_outbox` schema accepts only `model_breaker` and `fleet_halt` sources and their specific edge fields. An additive migration extends its source/check constraints for `fleet_control` and `qa_patrol_overdue`, adds the nullable `condition_episode_id` edge field with source-specific shape and unique index, and extends snapshot/payload allowlists to fixed condition ID, source category, and safe classification only. It preserves existing rows and source-specific uniqueness, forced RLS, fixed producer grants, claim guard, 90-day outbox retention, and Switchboard's sole delivery ownership. A condition can outlive its outbox retention; the condition record retains the immutable attention episode ID and terminal delivery category so read models remain honest, while historic outbox cleanup never authorizes a new send.

The first attention transition and outbox append should commit together when possible. A separately supervised reconciliation checks active due condition episodes for a missing attention link and repeats the fixed idempotent append, so a partial deploy or interrupted transaction cannot silently lose the owner alert. This repair never creates a second outbox episode for the same condition episode. Subsequent L2/L3/L3-repeat transitions stay in the condition ledger under its bounded schedule; they do not automatically reissue an outbox row. An explicit owner action can use the existing uncertain-episode reissue contract if its authorization and confirmation gates are met.

Switchboard's existing delivery worker claims `pending→sending` under its service lease and token/epoch fence. Extend only the fixed, content-blind formatter for the two new sources. Confirmed transport is `sent`, definitive rejection is `failed`, and ambiguous transport is `uncertain` with no automatic resend; only proven pre-transport no-effect failure may retry with bounded backoff. The owner-facing condition projection reads the linked outbox state and worker progress, distinguishing pending, sending, sent, failed, uncertain, and worker-unavailable without ever calling a pending send delivered. If Switchboard or its delivery target is down, the producer still persists intent and the UI reports unavailable; there is no independent external functional monitor in this change.

Alternative rejected: each stale daemon opening its own notification or QA investigation. A common observer/auth seam would flood the owner and still depend on QA's circular scheduler. Direct Messenger calls from the observer would bypass the outbox certainty fence.

### 5. Give `/ready` one stronger meaning and gate deployment on sustained function

`GET /health` and `GET /api/health` remain process-only. The public exact `GET /ready` introduced by active `k3s-deployment-helm-chart` is the single semantic readiness endpoint in both Compose and k3s. Retain its response shape: HTTP 200 `{"ready":true}` only when fully ready; HTTP 503 with `{"ready":false,"checks":{"postgres":false,"roster":true,"observer":false,"fleet":false,"qa_patrol":false,"supervisors":false,"route_canary":false}}` as an illustrative failure. Check keys are a fixed allowlist of booleans; no daemon names, endpoint addresses, payloads, secrets, or private state. The exact public path has no owner session; other API paths retain owner authentication.

`roster` means the exact configured expected set was loaded, not merely that one row exists. `observer` means a complete controller cycle advanced; `fleet` means every expected non-paused daemon is fresh, correctly identified, latest-epoch, accepting, and compatible under active policy. Explicit owner pause is an intentional exclusion; quarantine and ambiguous review are not. `qa_patrol` means a completed scheduled `clean`, `findings_dispatched`, or genuine filtered-finding `suppressed` cycle with current-config all-enabled-source success provenance within twice configured cadence; `running`, `error`, `skipped_overlap`, synthetic `suppressed`, and ambiguous legacy rows do not count. `supervisors` consumes the existing process-fenced supervised-job health projection only for named Dashboard lifespan loops, including the periodic observer and condition/attention producer when registered there; unavailable, unknown, stale, or stopped evidence is false. The Switchboard runtime-attention delivery worker is outside that projection and reports availability through the linked condition/outbox delivery state, not a falsely healthy Dashboard supervisor. The readiness implementation does not create a competing job-health store or System surface; the owning `bu-c6wjr` work must land first. `route_canary` runs a fixed, content-free Switchboard preflight for the lexically first non-paused configured domain target: it traverses the production route policy, registry eligibility, compatibility, and exact endpoint resolver, then makes one bounded identity GET through the shared verifier with a fixed timeout and schema. It requires a matching current-epoch, accepting response and a successful no-side-effect preflight result. If no such domain target exists or any step fails, the check is false. It creates no route inbox, session, notification, or ingestion record. This check proves the control-plane selection/reachability path, **not** transactional `route.execute` acceptance or downstream session success; target-delivery receipts and failure conditions provide separate evidence. The controller computes one bounded, cached readiness snapshot; an unauthenticated request does not trigger probes or expensive database fanout. If the snapshot is stale or absent, readiness fails closed.

The canonical launcher may keep Docker `/health` for process management, but deployment completion waits for at least two observer advances, multiple QA/controller checks, and a sustained interval longer than one liveness TTL with a passing dry-run canary. It emits a content-blind receipt identifying failed check categories, then classifies rollback. A green process during a five-minute post-restart registry window cannot pass. The exact timing and timeout are configurable with safe defaults; the acceptance invariant is the full-TTL boundary.

The active k3s delta's `Readiness probe endpoint` requirement is being reconciled to this stronger contract before both changes can archive. This changeset uses a differently titled requirement to avoid concurrent same-name `MODIFIED` overwrite. Existing external minimal `/api/health` polling remains its own approved operation. The separately specified unconfigured-deadman assurance condition records missing independent monitoring without inventing a failed ping or QA finding. A second external semantic monitor or synthetic route target is an explicit owner gate, not a side effect of this implementation.

Alternative rejected: creating another internal readiness endpoint. It would leave k3s `/ready` with a misleading weaker meaning and give deployment surfaces competing verdicts.

## Risks / Trade-offs

- Observer downtime or DB failure → return `observer_unknown`, keep prior condition open, and fail semantic readiness; do not stamp fabricated freshness.
- A valid old-process response arrives after a successor → server-allocated monotonic boot epoch fences it before probe-sequence comparison; verify registration rollback and concurrent periodic/on-demand races with real PostgreSQL.
- Historical quarantine provenance cannot be reconstructed → preserve evidence, use `review_required`, and require an explicit owner resolution before routing.
- Probe bursts load daemon ports → bounded concurrency, single-flight, deadlines, and cached readiness; readiness HTTP never initiates probes.
- QA intentional pause may make readiness false → show it as an explicit policy reason, not a healthy patrol; this is the honest deployment gate.
- Switchboard worker or delivery target is unavailable during a control-plane incident → retain one pending/failed episode and expose its status; independently supervise producer and worker progress, while external functional monitoring remains a separate owner gate.
- External send is uncertain → preserve terminal `uncertain` without automatic replay or a new escalation page; manual reissue retains the existing owner confirmation and lineage contract.
- A synthetic route can accidentally create effects or falsely imply delivery → use the fixed-target selection/policy/endpoint preflight and bounded identity GET with no inbox or session write; test negative side effects and keep transactional target acceptance as a separate receipt claim.

## Migration Plan

1. Add durable server-allocated per-daemon boot epoch registration plus separated state, policy provenance, and DB-reserved probe sequence. Preserve old fields as a read projection. Test bootstrap GRANT/RLS replay, monotonic registration, crash/retry, and rollback on real PostgreSQL.
2. Add daemon identity endpoint and Dashboard periodic observer in shadow mode; give Switchboard the narrow shared verifier and DB reserve/record path for one bounded on-demand probe. Verify exact roster binding, malformed/wrong identity, old epoch even with larger probe sequence, failure, and concurrent cross-process probes without changing route authority.
3. Classify legacy quarantine by provenance and review ambiguous rows. Compare old and new eligibility; do not cut over while unresolved rows are silently active.
4. Switch routing to receiver observation and bounded stale recheck; decouple local scheduler; enable fleet/QA conditions. Verify auth-enabled cross-layer routing across multiple TTL windows.
5. Extend the fenced runtime-attention outbox schema, fixed producer, and Switchboard formatter for fleet and QA condition episodes. Start the independent producer and missing-intent reconciler; verify one content-blind episode per condition under concurrent/restart/worker-down faults and all terminal delivery outcomes.
6. Strengthen `/ready`, launcher receipt, and sustained canary. Reconcile the active k3s `/ready` delta and owner-auth route allowlist before archive. Retire the old heartbeat POST/reporter only after the new path passes cutover tests.
7. Roll back code using the preserved schema/projection if required. Keep sticky policy, quarantine provenance, and any already-issued attention episode; rollback cannot authorize a previously denied target or resend an uncertain notification. Roll forward to retire old columns after all consumers migrate.

## Open Questions

The exact separate-host functional monitor endpoint, its provisioning, and any late delivery of historical ingestion are future owner-gated work. They do not affect the internal liveness/readiness contract.
