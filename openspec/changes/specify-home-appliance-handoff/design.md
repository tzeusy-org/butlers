## State and ownership

Home owns `appliance_bindings` (binding UUID, source refs, mapping/profile revision, generation, enabled, source watermark) and `appliance_cycles` (binding/generation/start identity, phase, observed/received times, evidence digests, coverage, terminal reason). A separate Home-owned handoff record references that cycle, with state `pending/snoozed/done/expired`, revision, action generation, immutable source enrollment generation and expiry, next reminder, allowance used and canonical delivery subject ref. These are domain facts, not a second shared perception or delivery ledger. Observation/reminder generation and handoff action generation are distinct fences.

Machine phases: idle -> running -> completed/error; timeout/gap -> unknown. Recovery starts a new cycle only through the profile's fresh-start rule. Machine completion and handoff creation plus one durable delivery intent commit together. The existing canonical delivery writer consumes this intent idempotently; use the delivery subject's uniqueness, not a second provider-send implementation. A Home outbox is an atomic domain intent bridge, not a new notification ledger. Delivery uncertainty remains unknown and reconciles by the original subject/surface/generation.

Stop increments the enrollment generation and cancels/fences pending observation/reminder intents at the same Home transaction boundary; the canonical delivery service must revalidate that generation before send. It also increments open handoffs' action generation/revision and queues canonical presentation refresh with Done-only actions. Mapping changes use the same invalidation. Old callbacks fail the Home action-generation check even before presentation retraction finishes; refreshed Done binds the new action generation while preserving the original cycle provenance. Refresh updates existing presentation/read state and does not send a new reminder. A send already committed before Stop retains its receipt and is not described as recalled. Done closes only a pending/snoozed handoff; it never sends a device command. Later requires pending/snoozed state plus active unchanged enrollment, uses handoff revision CAS, decrements its finite allowance and replaces any pending reminder. Done/expired are immutable terminal states. Repeated identical action identity/digest returns the original receipt; changed bytes under that identity refuse. Done against an expired handoff refuses and reports expired; editing historical completion is outside this feature.

## Capability and presentation boundary

Proposed brokered Home operations are `appliance_watch_create` (exact source/mapping/profile, owner-authenticated), `appliance_watch_stop` (binding/current revision), `appliance_handoff_list` (bounded, maximum 50 rows) and `appliance_handoff_decide` (handoff ID, expected revision, action Done/Later and idempotency key). Mutations accept authenticated owner context from the existing dashboard/broker, never a body owner ID. Creation is explicit enrollment, not an inference from discovery. Raw HA text is data, not authority or an executable callback. No operation grants HA service execution.

Entry: Devices -> Appliance handoffs -> enroll an available device; unsupported rows explain the missing phase/freshness capability. The card leads with `Washer finished · Transfer load`, then separate human state, observation age and reminder. Done is the primary control; Later and Stop watching are secondary. Repeated controls reuse action identity; callbacks carry RFC0038 S6 subject/action/argument/owner/surface/generation/expiry bindings and require authentication. Device/source failure retains the last value labelled stale and an actionable reconnect message. No fake optimistic completion, hover-only state, duplicate toasts or competing approval surface. Use Dispatch tokens, focus behavior and keyboard-accessible controls.

## Failure reporting boundary

Five-second miss detection assumes a live recorder or caller. If persistence/control-plane service is unavailable, the live API/UI caller surfaces timeout or unavailable within five seconds and never confirms the operation; durable reconciliation later preserves the original deadline and failure timestamps. A complete process/host outage is outside the supported latency conditions and is reported as an outage on recovery, never as timely success or proof of a durable write during downtime.
