## Context

Home Assistant presence history contains provider-native person IDs. Chronicler
can attach those rows to canonical identities only when
`connectors.home_assistant_persons` contains the owner's exact mapping to an
existing `public.entities` row. The current migrated schema supports a direct
`entity_id` foreign key and allows entity-only rows; it deliberately does not
infer mappings.

The two identifiers form private household identity data. They must be entered
only by the owner and must never cross an LLM/session or general observability
surface. The dashboard currently has two distinct authentication contracts:

- `ApiKeyMiddleware` is optional and fails open when `DASHBOARD_API_KEY` is
  absent. It is insufficient for this route.
- `require_dashboard_owner_control` fails closed: absent configuration is `503`,
  and a missing or wrong `X-API-Key` is `401` after constant-time comparison.

The frontend does not yet have an approved way to supply that credential.
`bu-pb6oy` owns that decision. `authenticated_principal()` merely records that
an already-authenticated single-user request is attributed to `owner`; it does
not authenticate a request and cannot substitute for either boundary.

## Goals and non-goals

Goals:

- Accept a small, exact batch through one dashboard-only HTTP mutation.
- Preserve owner authority: no name, alias, display-label, or provider lookup
  may propose or infer a binding.
- Serialize mapping decisions, make replay deterministic, and refuse remaps in
  either direction without partial mapping writes.
- Make all client-visible and operational evidence content-blind while retaining
  an aggregate audit receipt.
- Define the tests and independent approvals required before implementation or
  use.

Non-goals:

- No mapping insert, update, delete, rollback, remap, repair, or verification
  against real data in this change.
- No entity creation, merge, promotion, rename, alias lookup, or role change.
- No Home Assistant API, snapshot, credential, secret, provider payload, or
  connector read.
- No new authentication mechanism, browser credential transport, or bypass of
  `bu-pb6oy`.
- No MCP tool, LLM prompt, session, scheduled job, CLI, direct-SQL operator
  workflow, background retry, or ingestion path.
- No restart, replay, checkpoint or watermark change, synthetic transition,
  production operation, deployment, merge, or queue authorization.

## Decisions

### D1: One body-only batch endpoint

The sole write surface is `POST /api/home/person-mappings`. It accepts no path
or query parameters. The JSON body is:

```json
{
  "mappings": [
    {
      "ha_person_id": "<exact-person-domain-id>",
      "entity_id": "<existing-person-entity-uuid>"
    }
  ]
}
```

`Idempotency-Key` is a required header generated by the dashboard as 32 random
bytes encoded as 43 unpadded base64url characters. It is unrelated to either
identifier and is never editable by the owner. The API hashes it before durable
lookup with SHA-256 and never stores or emits the raw header. The canonical
request digest is SHA-256 over canonical JSON whose pairs are sorted by the
byte-for-byte Home Assistant ID and then canonical UUID, so batch order does
not change request identity. Neither digest leaves the server-side receipt
record.

The body is limited to 32 KiB and one through 50 mappings. Each object permits
only the two named fields. `ha_person_id` is accepted byte-for-byte only when it
matches `\Aperson\.[a-z0-9_]+\Z` and is at most 255 UTF-8 bytes; it is never
trimmed, case-folded, normalized, completed, or resolved from a name.
`entity_id` must be a lowercase hyphenated RFC 4122 UUID string. A repeated
Home Assistant ID or repeated entity UUID
within one batch is a content-blind `422`, including an identical repeated pair.
The error never names a field position or value.

The dashboard may let the owner select an entity from the existing entity
surface, but submission sends only its UUID. The form must keep both values in
ephemeral component memory and clear them after settlement or dismissal. It
must not place them in a URL, navigation state, local/session storage, query
key, mutation cache retained after settlement, analytics event, console output,
or rendered error. This change adds no mapping-list or mapping-detail read API.

### D2: Fail-closed owner control is a prerequisite, attribution is separate

The route must authenticate through `require_dashboard_owner_control` or an
owner-approved successor with the same fail-closed guarantees before any layer
reads or buffers the request body, generates a receipt, acquires a database
pool, or observes protected state. Missing configuration returns `503`; a
missing or mismatched credential returns `401`; neither outcome reads or audits
the body.

Only after that gate succeeds may the handler call
`authenticated_principal()` to obtain the audit actor. No request model, header,
query parameter, or body field may assert the actor. The literal actor label
`owner` is attribution, not evidence that authentication happened.

The existing browser-auth decision `bu-pb6oy` is a hard prerequisite for the UI
and for claiming the workflow usable. This contract neither chooses a cookie,
JavaScript-held key, build-time key, nor same-origin bypass. Until the approved
`bu-pb6oy` mechanism is implemented and proven, the mapping UI must not ship and
the backend route must not be described as an available dashboard workflow.

### D3: One mapping-specific lock and one transaction decide the batch

Every authenticated, structurally valid request executes on one database
connection in one transaction. Before the idempotency lookup, entity-reference
checks, mapping reads, or mapping inserts, it takes the transaction-scoped lock:

```sql
SELECT pg_catalog.pg_advisory_xact_lock(
    pg_catalog.hashtextextended('butlers:dashboard:ha-person-mapping:v1', 0)
);
```

This one fixed, mapping-specific lock serializes all batches and all checks in
this workflow. No per-entry lock order can deadlock or permit two concurrent
batches to approve opposite sides of a remap.

Under that lock the server:

1. Looks up the hashed idempotency key. A stored key with the same canonical
   request digest returns the stored terminal receipt without reading or writing
   mappings. The same key with a different digest returns a fixed
   `IDEMPOTENCY_CONFLICT` `409` with zero mapping writes.
2. Selects every distinct referenced row from `public.entities` in ascending
   UUID order with `FOR UPDATE`, without filtering invalid rows out of the lock
   query. It retains every acquired row lock through the mapping, receipt, and
   audit commit, then evaluates the locked rows using the actual live predicates
   `metadata->>'merged_into' IS NULL` and
   `metadata->>'deleted_at' IS NULL` plus `entity_type = 'person'`. Missing,
   tombstoned, merged, and wrong-type targets are one `INVALID_REFERENCE` `422`
   category. Only the aggregate `invalid_reference_count` is exposed; existence
   and type are not distinguished.
3. Reads all existing `connectors.home_assistant_persons` rows matching either
   side of the proposed batch. An exact pair is unchanged. A Home Assistant ID
   mapped to any other or null entity, or an entity UUID mapped to any other
   Home Assistant ID, is a mapping conflict. Legacy rows are observed but never
   repaired or filled in by this endpoint.
4. If any conflict exists, commits only the content-blind receipt/idempotency and
   audit evidence and returns `409 MAPPING_CONFLICT`. It inserts, updates, and
   deletes zero mapping rows. Otherwise it inserts all new entity-only rows and
   the success receipt/audit atomically; exact pairs remain untouched.

An authenticated, structurally valid request records its terminal aggregate
receipt for success, invalid reference, or mapping conflict, so an exact key
replay cannot change outcome after later database state changes. Structural
validation failures do not create durable idempotency state because no canonical
mapping set exists.

The idempotency record stores only a digest of the raw key, a canonical request
digest, the opaque receipt, aggregate counts, completeness, outcome, fixed
failure category, and timestamps. It stores no raw key and no request body or
identifier copy. Records do not expire in v1; retention or deletion requires a
separate approved contract. A failed transaction leaves neither a partial
mapping batch nor a success receipt.

Submitting an already-present set with a fresh key is a successful identical
no-op: `created_count = 0`, every submitted pair contributes to
`unchanged_count`, and no mapping row is updated. Replaying the same key and
body returns the original receipt and counts exactly.

The referenced-row locks establish the interaction with concurrent entity
lifecycle mutations. An entity merge, metadata tombstone/delete, physical
delete, or `entity_type` change that owns the entity row first must finish
before the mapping query can lock and inspect it; the mapping then observes the
committed invalid state and returns `INVALID_REFERENCE`. If the mapping
transaction locks and validates the entity first, the entity mutation waits
until the complete mapping/receipt/audit decision commits. The receipt proves
the mapping was complete at that serialization point; it is not a lease against
a separately authorized later entity lifecycle change. PostgreSQL may then
apply that later change, including the existing foreign-key action on physical
delete, only after the mapping decision is durable. A deadlock or aborted
transaction produces no partial mapping or success receipt.

The fixed mapping lock also serializes idempotency-key creation. Simultaneous
same-key/same-request callers must produce exactly one durable terminal
idempotency record; the first decision commits it and every waiter returns that
record's identical receipt and counts. For simultaneous same-key/different-
request callers, the first lock holder alone owns the durable terminal record.
After it commits, every loser returns fixed `IDEMPOTENCY_CONFLICT`, creates no
second idempotency terminal record, and performs zero mapping writes. A loser
may emit its separately allowed content-blind refusal audit, which is not an
idempotency terminal record.

### D4: Receipt and errors are aggregate-only

The server generates an opaque UUIDv4 receipt unrelated to the body or
idempotency key. A new, mixed, or identical no-op success returns `200` in the
standard `ApiResponse` envelope with exactly:

```text
data.receipt
data.complete
data.received_count
data.created_count
data.unchanged_count
data.conflict_count
data.invalid_reference_count
meta
```

`meta` is empty. No identifier, mapping, entity name, alias, provider datum,
request digest, idempotency key, row ID, table name, field position, or submitted
value is returned. `complete` is true only when the complete submitted mapping
set is already present after the transaction. On success,
`received_count = created_count + unchanged_count`, with both refusal counts
zero.

Non-2xx responses use RFC 0007's standard error envelope and a fixed code and
message. Every post-authentication terminal response includes a receipt; its
structured `error.details` contains only that receipt, the completeness flag,
and aggregate count fields. A mapping or
idempotency conflict is `409`; structural/duplicate input or an invalid entity
reference is `422`; an unavailable database is `503`. Errors never identify the
offending member, distinguish missing from wrong-type references, echo a value,
or include driver/provider text. Mapping failures always report
`created_count = 0` because no mapping write committed.

There is no verification endpoint. An exact idempotent replay is the only API
confirmation and returns the same aggregate receipt. Direct database inspection
is allowed only inside the future isolated real-PostgreSQL test harness, never
as the operator workflow.

### D5: Request capture, audit, logs, and telemetry are explicit allowlists

The endpoint must be exempt from `DashboardAuditMiddleware` body reading and
generic path-parameter collection before it is mounted. Redacting field names
after the middleware has buffered the body is insufficient. The route emits one
explicit audit event named `home_assistant_person_mapping_batch`; its allowlist
is:

- server-derived `actor`;
- opaque `receipt`;
- `received_count`, `created_count`, `unchanged_count`, `conflict_count`, and
  `invalid_reference_count`;
- `outcome` from a fixed enum;
- optional `failure_category` from the fixed enum `request_invalid`,
  `reference_invalid`, `mapping_conflict`, or `idempotency_conflict`.

Audit `target`, `note`, request summary/body, path parameters, error text,
provider response, raw idempotency key, request digest, and both identifiers are
absent. Success audit evidence participates in the mapping transaction. A
refusal may commit its receipt/idempotency and content-blind audit evidence while
committing zero mapping rows; inability to audit must never turn a refusal into
permission or a partial write.

Application and access logs use only the route template, fixed outcome/failure
category, and aggregate counts. They never log the request URL as supplied,
headers, body, receipt, identifiers, exception rendering, SQL arguments, or
provider data. The route accepts no URL parameters.

Metrics and traces may carry only low-cardinality fixed outcome/failure-category
values and numeric aggregate counts. No raw or hashed identifier,
idempotency-key material, request digest, receipt, body, header, entity name,
SQL argument, exception string, or dynamic URL may become a metric name/label,
span attribute/event, baggage value, or resource attribute.

No prompt, session record, tool call, model input/output, MCP resource, MCP tool,
connector event, notification, or Beads record may receive the request, either
identifier, the idempotency key/digests, or a mapping detail. The endpoint must
remain absent from every generic MCP and runtime tool registry.

## Risks and trade-offs

- A single fixed lock serializes rare operator batches. The bounded batch keeps
  the critical section small; serialization is preferable to remap races.
- A count can reveal household size. The owner-authenticated caller already
  supplied the batch, and aggregate counts are the minimum evidence needed to
  know whether it completed. No unauthenticated response includes them.
- Durable idempotency evidence adds storage. Unbounded retention avoids a replay
  window that could silently expire; a later retention policy needs separate
  privacy and replay analysis.
- The current browser cannot yet reach fail-closed owner-control routes. Keeping
  `bu-pb6oy` explicit prevents this spec from laundering an unresolved
  credential-transport choice into implementation.
- Existing conflicting or legacy-null mappings are refused, not repaired. Any
  remap, delete, rollback, cleanup, or historical-data correction is a separate
  owner-approved workflow.
