# Parked-notification review correlation

## Current source and released intent

Pinned baseline `0ddffff31afefd41ae43e83508e4a02fd916adda` has a pool-scoped approval hook and transactional `ParkAdmission` returned after the park transaction exits. Messenger recipient gates receive its action UUID but raise a ValueError containing it; the route/notify refusal keeps only error text. Switchboard `_deliver_via_notify_request()` copies caller metadata, records a failed notification and discards the structured action identity. `log_notification()` binds a mapping through the existing JSONB codec. Both notification lists and mark-read project metadata and error; the feed has Session and Trace links only. The adopted dossier is `/approvals/{id}`, not historical `/approvals?id=`.

`notify()` also has local `pending_approval` and missing-identifier parks. Their status/defaults and `pending_action_id` are compatibility controls, not an excuse to synthesize a Switchboard row or broaden this routed seam. Approval request/recovery intents must not recursively park or enter this ordinary history seam.

## Exact proposed representation and authority

Select a dedicated nullable JSONB `switchboard.notifications.approval_review` column, not a reserved key in ordinary metadata. Its only admissible object has exactly `action_id` (canonical 36-character UUID string) and `butler` (literal `messenger`, taken from the actual registered target/configured owning daemon). Null is no recorded correlation, not proof that no action was parked. A bounded type/check migration belongs to later implementation and does not alter roles, tables, bootstrap authority or existing rows beyond nullable compatibility.

The core typed refusal/response carries the same two-field `approval_review` only when the pool-scoped recipient decision is a successful `parked` result containing the durable UUID after commit. The Messenger producer derives owner identity from its actual pool/config and target binding, never notify input origin/metadata. The reference is an additive field beside the ordinary error, not a new successful delivery or recovery capability. The registered Switchboard-to-Messenger route must bind schema, matching actual request ID/channel and registered response target; mismatched, malformed, missing, parking-failed or unknown responses cannot supply it. Caller input cannot select this field. The Switchboard writer uses a separate trusted argument at its own internal seam; generic metadata/log inputs cannot populate it. Legacy metadata named `approval_action_id`, embedded `action_id=...`, decoded `_raw`, and similarly shaped caller objects never become authority.

## Persistence, transactions, failure and replay

The approval park and optional durable delivery intent commit atomically in Messenger's existing owning transaction. Switchboard subsequently inserts the existing failed notification and its admitted reference together in its own single INSERT. This is two owning transactions over MCP, not a distributed transaction or direct Switchboard read of Messenger schema. A park rollback/failure supplies no reference; a later notification insert failure does not unpark, fabricate a ledger row or retry delivery. It remains a truthful logging failure/unknown read. Existing best-effort ledger semantics and retryability/failure classifications survive. Lost response has no reference and is not an inferred successful park. This work adds no replay/park deduplication: an existing duplicate admission returns its actual admitted action UUID; different attempts must not borrow another action. No error-string backfill of old rows. Removal of the added field restores existing behavior; rollback must retain existing pending actions/history rather than deleting them.

## Independent read admission and dossier identity

API uses its existing authenticated dashboard DatabaseManager boundary, not daemon cross-schema access. It projects `approval_review` as that bounded object or null and `approval_review_state` as `available`, `none`, or `unavailable`. Missing legacy column/row reference is `none` (no recorded reference); corrupt/wrong-source references or failed/incomplete verification are `unavailable`, never complete/no-approval. A failed notification-source read retains the existing `source_available=false` contract independently.

Before emitting `available`, the reader resolves the recorded UUID through the existing configured approvals pools under current auth. It must positively find the committed action in the recorded Messenger pool and prove exactly that unique owning result across every applicable pool, with complete successful source enumeration/read. Current dossier lookup is first-match; first-match or bare UUID cannot prove same-action identity. A duplicate ID in another pool, an unavailable required pool, wrong recorded owner or absent action withholds the link. The adopted `/approvals/{id}` route path remains; the review door carries fixed `?review_source=messenger`. The mounted dossier forwards this expected source to its authenticated `/api/approvals/{id}` GET. That qualified GET repeats complete unique same-source/action resolution and refuses missing, ambiguous, wrong-source or unavailable results without first-match fallback. A source change between feed and click therefore cannot silently open another action. Ordinary unqualified dossier doors retain their existing contract; this additive read constraint adds no permission or mutation authority. Reads are finite and page-bounded (existing max200), batched/grouped by configured pool rather than unbounded per-row fanout; no raw tool args, recipients, message, error diagnostics or credentials are added to correlation. The later implementation must position real same-action SQL readback and ambiguity/degradation controls, not canned-row equality alone.

## Dashboard behavior

A failed/blocked row with admitted `available` reference displays a real `Review approval` Link to `/approvals/{action_id}?review_source=messenger`. The UUID is validated/encoded; no arbitrary URL or caller-provided path is used. It is keyboard-operable with existing visible focus styling. It leaves failed/effective-status badges, errors, message expansion, session/trace links, triage handlers, loading skeletons, filters, totals and pagination intact. Opening the link is a GET/navigation; the dossier retains all existing server-derived authorization/redaction and explicit decision controls. Decision/status changes do not grant delivery permission from the feed. No optimistic successful/approved state is inferred.

`unavailable` is a named row-local review-reference-unavailable state without an interactive door, while other rows and session/trace doors remain usable. `none` supplies no review link and makes no claim that approval was unnecessary. Ordinary genuine failed deliveries with no park retain their failure behavior. Correlation does not make notification-source degradation an empty/healthy stream.
