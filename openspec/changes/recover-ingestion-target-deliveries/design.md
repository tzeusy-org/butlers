## Context

See `proposal.md` for the incident. RFC 0003 places classification and `route.execute` under Switchboard. Today `src/butlers/modules/pipeline.py` can execute a target route during an LLM `route_to_butler` tool call or decomposition fan-out, then persist `message_inbox` classification and dispatch outcomes afterward. `src/butlers/core/route_inbox.py` mints a fresh UUID on each target acceptance. `src/butlers/core/ingestion_events.py::ingestion_event_replay_request` handles a failed ingestion row with a status-only `failed -> ingested` write and handles `ingested`/`replay_failed` by setting `replay_pending` then resetting `message_inbox` to `accepted` for fresh classification. Those seams cannot prove or safely retry a missing target handoff.

The accepted `repair-whatsapp-identity-reconciliation` change already modifies `conversation-decomposition`'s `Multi-Butler Fan-Out from Single Ingestion` requirement and introduces distinct `segment_id`/`subrequest_id` for multiple concepts sent to one target. This change does not restate that active MODIFIED block; it adds durable identity and adjusts the separate storage requirement. Dashboard synchronous routing, Messenger, domain events, and connector ingress have their own delivery contracts. The existing `TransportOutcome` vocabulary (`confirmed`, `not_attempted`, `rejected`, `uncertain`) is the outcome authority for this lane.

## Goals / Non-Goals

**Goals:** Make the classified target set and every target obligation durable before dispatch; let the target return one stable acceptance receipt; retry only proven pre-accept transient work; show partial and ambiguous outcomes truthfully; provide a bounded owner-reviewed path for historical late delivery.

**Non-Goals:** Re-run classification during delivery recovery; infer a failed target session from target acceptance; recover dashboard turns, Messenger sends, domain-event subscribers, explicit misroute corrections, or connector/provider ingress through this outbox; rewind source cursors; auto-send historically late material without exact owner approval.

## Decisions

### Decision 1: Classification produces a durable plan before side effects

For this lane, the LLM's `route_to_butler` calls become classified decisions collected during the session; the tool cannot call a domain target until the complete decision set is validated and committed. Triage bypass, no-tool fallback, and conversation decomposition use the same handoff. Store the immutable normalized route payloads, target names, and stable segment IDs in Switchboard ownership alongside the parent `message_inbox` classification/decomposition result and per-target intents in one PostgreSQL transaction. A failed transaction leaves no target call. A duplicate ingress reads that committed plan. A worker may immediately dispatch the newly committed intents to preserve latency; the persistent worker can take over after a crash. A plan is never reconstructed from model output after target dispatch.

The ordinary decomposition segment key derives from the committed concept ordinal and target, preserving the active WhatsApp change's distinct segment/subrequest identities. The code-authoritative calendar proposal special case remains outside this ordinary `route.execute` lane. Empty/skip/metadata-only outcomes commit their normal classification result and no delivery intent. Directly routing from the classification tool is rejected because its side effect precedes durable target-set persistence.

### Decision 2: Target acceptance owns one route-inbox row per delivery key

Use `(ingestion_event_id, target_butler, segment_id)` as the logical delivery key; bind the target name to the receiving daemon identity. Add a target-schema uniqueness constraint or narrow acceptance table that atomically upserts that key with one `route_inbox` row ID and a digest of the canonical immutable route payload. A duplicate, concurrent call returns the original receipt only when its target binding and payload digest match; a same-key/different-payload call returns a conflict without changing the original. Validate the parsed route envelope, require `source_endpoint_identity="switchboard"` to be allowed by the receiving daemon's existing `trusted_route_callers`, require the target name to equal the receiving daemon name, bind the event key to `request_context.request_id` and the segment key to its target-visible subrequest, and reject malformed or mismatched keys before acceptance. The existing caller identity is asserted in the route envelope and is not cryptographic authentication; this contract relies on the adopted trusted-host MCP boundary. A future untrusted-host topology requires a separate service-auth design and approval. The receipt is the accepted row identity, not a session-completion claim. Target route-inbox leases continue to own crash recovery after acceptance. A read-only receipt lookup through the same constrained internal route surface must carry and compare the original key, receiving target, and canonical immutable payload digest. A mismatch returns conflict; only an exact match returns an opaque receipt, never the stored payload. This prevents a same-key altered route from impersonating a confirmed delivery.

### Decision 3: Fenced worker state follows transport certainty

Store `pending | attempting | accepted | retry_wait | ambiguous | terminal_failed`, a monotonic fence/claim token, server timestamps, bounded next-attempt time and budget, and allowlisted safe reason evidence. The worker rechecks current route eligibility before every attempt. `confirmed` with a valid receipt moves to `accepted`. A transient `not_attempted` outcome such as unreachable target can enter `retry_wait`; policy-denied `not_attempted` is terminal. `rejected` is terminal. `uncertain`, a post-start transport exception, or a reclaimed `attempting` lease without affirmative pre-transport proof enters `ambiguous`. Reconciliation may query the same target key for a receipt and promote it to `accepted`; no receipt leaves the intent ambiguous. No automatic second call occurs after uncertainty. Backoff has jitter, an attempt cap, and an age cap configured as operational tuning, with closed safe reason values. An exhausted safe retry becomes visible `terminal_failed`.

The transport envelope's legacy top-level `retryable` boolean is not enough to authorize a retry; the canonical outcome and policy reason must agree. This reuses the already shipped transport certainty contract rather than defining another taxonomy. `accepted` is terminal for the Switchboard outbox. A target session later failing is a separate target-session concern and does not trigger resend.

### Decision 4: Per-target truth derives the event summary

Store per-target intent state separately from the immutable plan and project a content-blind aggregate into ingestion list/detail APIs. A partial fan-out keeps each accepted receipt and retries only eligible failed segments. The event can say delivery accepted only when every selected target has an accepted receipt; an unavailable intent store produces an unavailable projection, not a zero-target success. Existing `message_inbox.dispatch_outcomes` remains a per-butler compatibility aggregate refreshed from intents, with a non-complete result if any same-butler segment is unresolved; authoritative per-segment status and receipts remain in intents. `message_inbox.lifecycle_state = 'routed'` follows only when all ordinary target segments are accepted. Existing `public.ingestion_events.status = 'ingested'` means the source was accepted or processed and can coexist with an unresolved target; it is never universal target-acceptance evidence. No API treats a queued intent as downstream session completion.

### Decision 5: Failed-event recovery uses intents, never a status-only flip

Keep the existing endpoint shape where possible, but split its policy by source table. For `public.ingestion_events`: `failed` queues only a safely retryable original target intent; `ingested` and `replay_failed` may queue only an outstanding original safe intent and otherwise return a conflict; `replay_pending` returns the same queued identity idempotently, while a legacy orphan pending marker is projected as unavailable/conflicting; every other status returns a conflict. No public-event branch resets `message_inbox` to `accepted`, reclassifies, or sends an already accepted target. The status mutation and intent queue transition share one transaction. A request cannot report pending unless work is durably queued, and it cannot clear a failed routing event merely by changing a status column. Subsequent target receipts may support a separate evidence-backed source-status reconciliation, but the coarse `ingested` status itself never proves all targets accepted. For `connectors.filtered_events`, preserve the current connector-policy-gated `filtered | error | replay_failed | ingested | replay_complete -> replay_pending` drain contract; `replay_pending` does not enqueue twice. Preserve email replay safety. In the Timeline, show target state in the existing row/drawer hierarchy, acknowledge the action immediately, and expose an accessible reason when recovery cannot run. Do not display an optimistic successful replay.

### Decision 6: Historical recovery is a separate exact owner gate

The historical dry run performs read-only, content-blind joins across retained event, inbox, route, and target receipt evidence. It groups counts by time bucket, channel, target, and safe failure class and privately produces an exact key set with evidence class. Only canonical `not_attempted` or equivalent independently proven no-effect attempts with retained target payloads are candidates. Accepted, ambiguous, rejected, policy-denied, pruned, and unprovable rows are exclusions. A missing receipt alone is never proof of non-acceptance, but a pre-cutover stale-target refusal may qualify when its independent no-attempt evidence is intact even though no receipt exists. If no old row has sufficient evidence, the eligible set is empty. The owner approves a bounded age/channel policy and exact set; admission then rechecks each key and atomically creates only those approved intents. It never rewinds a provider cursor, replays connector ingestion, or silently delivers all rows from an hour or channel.

### Decision 7: Recovery evidence stays content-blind

The outbox may hold the minimum target payload needed for delivery under existing data access and retention controls, but API/log/metric/condition/dry-run projections use allowlisted state and reason codes, bounded target/segment identifiers, and counts. Raw messages, sender identities, provider payloads, exceptions, and credentials never enter these projections. Schema checks reject unknown state/reason combinations. The recovery worker gets narrow rights over Switchboard intents and routes through the existing MCP boundary; it receives no direct access to target-butler tables.

## Risks / Trade-offs

- **Classification latency:** collecting decisions before dispatch delays the first target call until plan commit. Use immediate post-commit dispatch on the same durable worker path and measure this interval.
- **Cross-boundary migration:** rolling versions may not yet understand delivery keys. Add target acceptance representation first, then propagate the stable key and persist intents in shadow mode, then enforce no-call-before-commit and automatic safe retry. A target that cannot return a stable receipt must not be treated as confirmed under the new lane.
- **Historical evidence quality:** old rows may lack enough proof or payload. The dry run must prefer an empty eligible set over inferred safety.
- **Retention:** target payload and intent retention must cover their retry/owner-review window; expiration converts unfinished work to a visible terminal state before pruning, without erasing audit lineage. Keep content-bearing retention no longer than the governing ingestion policy permits.
- **Concurrent workers and schema rollback:** fence state transitions and rely on the target uniqueness constraint. Disable new admissions/retry workers before rolling back code; retain newly written intents and receipts for diagnosis rather than dropping them while work remains.

## Migration Plan

1. Add inert Switchboard intent representation and target acceptance key/receipt storage with uniqueness, safe enums, grants, and migrated real-PostgreSQL tests. Backfill no historical event automatically.
2. Propagate stable identities through all ordinary non-dashboard classification, triage bypass, fallback, and decomposition paths. Shadow-compare intended target sets and evidence without enabling automatic retries; prove dashboard/Messenger/domain-event/connector paths remain on their existing contracts.
3. Make the committed plan authoritative before target calls; enable fenced dispatch and safe retry only after every target daemon can return stable receipts. Remove the status-only failed-event transition and wire truthful API/UI states in the same release boundary.
4. Run multi-TTL fault-injection and real-PostgreSQL acceptance tests, then perform the content-blind historical dry run. Historical admission remains inactive until an exact owner approval.

Rollback disables new intent admission and workers, preserves persisted state and accepted target receipts, and restores the prior ordinary route path only after a controlled compatibility check that cannot replay accepted or ambiguous intents. It never drops delivery evidence as a rollback shortcut.
