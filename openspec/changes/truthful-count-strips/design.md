This complete Alternative A protocol was proposed at a6f342bd54c207b9e672d7d4e51be6af6d4f2876, independently assessed at protected 6cfc4eeac9003c0321a892d02b9865113cdccb72, and accepted into all four canonical issue fields before explicit SOURCE release. ## D1. Meaning and source authority

The original outcome and examples remain: a missing-heartbeat bucket renders `not listening`, hours 5–7 in the planted API example are `deaf`, and the accessibility example says `not listening 3h`. These literals do not prove provider outage or physical receiver availability. The proposed precise meaning is **no durably accepted heartbeat in a closed interval covered by positively established complete receiver recording**. A packet merely sent but never durably accepted is outside the accepted receiver-observation contract. Expose this qualification in the legend and accessible description; never imply Gmail/provider failure or that every instant of the hour was healthy. This is an explicit normative qualification of the original word `sent`, not an undisclosed redefinition.

The protected pre-change implementation cannot establish that coverage. Registry persistence is fatal, while partition/log failures are caught after registry acceptance. Gmail commits classification admission before those best-effort steps. A successful history read establishes only that the read worked. Empty history, flanking positive heartbeats, first_seen_at, nominal retention, latest registry recency, healthy events, sibling endpoints, or current receiver status do not establish append completeness. The current last_heartbeat_at overwrite is not monotonic under racing submissions. Absence-only current-source buckets therefore remain UNKNOWN; an independently readable positive accepted heartbeat is evidence for its own bucket only. An all-UNKNOWN replacement does not fulfill the original DEAF outcome and cannot close the bead.

LIVE means at least one exact-endpoint accepted receiver heartbeat in the bucket, OR across actual instances of that endpoint. `healthy`, `degraded`, and `error` are all positive process-heartbeat observations under Connector Liveness and Eligibility; the independent provider-health state remains visible and unchanged. LIVE does not mean all-hour coverage, source-health success, expected-signal measurability, administrative eligibility, or current routing authority. Expected-signals continues to require its own healthy/current exact-endpoint predicate. No heartbeat from a sibling endpoint, checkpoint row, unknown-role row, or another namespace is substituted.

## D2. Alternatives and explicit amendment

A — **Recommended complete durability alternative:** strengthen the existing history INSERT and registry UPSERT into one transaction, establish a server-owned coverage boundary only from a matching same-transaction append, and make the coverage evidence resistant to ordinary permitted runtime DML. Retain two per-heartbeat DML statements, existing retention, non-blocking connector failure handling, and direct SQL producer compatibility. Bounded xid/coverage metadata adds row/WAL bytes; byte volume and latency are unmeasured and no savings are claimed. No additional write frequency or DML operation is introduced. Explicit changes are a nullable registry coverage structure, a database-stamped transaction identity on newly appended log rows, integrity guards, and changed handler commit/ACK semantics. No new role, privilege, signer, provider call, metrics dependency, or extra heartbeat DML is proposed. The coordinator allocated **switchboard-chain sw_041/down_revision sw_040** for this released source implementation. Do not amend applied migrations or chain to unpublished core260/261/capture259.

B — Atomic application writes plus an externally attested deployment/activation fence, without database guards. This uses the same two DML writes but cannot survive the existing supported registry-only SQL producers, ordinary allowed log mutation, or an old handler during rollout without additional protected writer exclusion. Those controls do not currently exist as adopted per-bucket authority. Reject as the default because it invents provisioning/rollout authority and risks false completeness.

C — Keep current best-effort writes and show positive observations plus UNKNOWN for missing history. This is safe under the original read-only/no-writes boundary, but it leaves the literal missing-hours-DEAF and not-listening examples UNMET. It is not the recommended delivered substitute and is not an implicit deferral of S2.

The original `No new writes` is retained verbatim in the four-field packet. Alternative A proposes the precise qualification **no dashboard writes, no additional per-heartbeat DML/write operations; stronger atomicity and integrity of the two existing writes**. This is a real contract amendment to failure/commit semantics and schema, not an assertion that the original text already authorized it. The stronger history requirement and Gmail ordering prose must be reviewed as a whole before canonical application/SOURCE release. Default before that review is unchanged source, unchanged original criteria, no enactment. No generic owner gate or permission question is created.

## D3. Complete proposed writer/coverage protocol — corrected lock and integrity boundary

Use the existing trusted migration/object owner and existing normal SET ROLE identities. Bootstrap gives the own-schema butler role SELECT/INSERT/UPDATE/DELETE/TRIGGER/REFERENCES and function EXECUTE; connector_rw has operational-table DML. These actual source grants are preserved. Ordinary TRIGGER privilege is a capability to install interference, not evidence that interference is impossible. No grant, role, signer, runtime exemption, SECURITY DEFINER mint function or extra heartbeat DML is added. Runtime roles must not own/alter the protected parent, children or functions, disable guards, set session_replication_role, or use the trusted migration connection for domain evidence. Actual migrated role/catalog controls must establish this; trusted migration-owner/administrator mutation and backup rollback remain outside the guarantee.

The proposed nullable registry heartbeat_history_coverage JSONB remains version=1, UTC coverage_start and bounded catalog-derived partition receipts (range_start, range_end, partition_oid) for the conservative seven-day horizon and precreated next month. Log recording_xid remains nullable xid8. Upgrade preserves every old row/body/received_at; NULL old rows cannot certify preactivation. No backfill, independent stamp table, per-heartbeat receipt INSERT or extra write is introduced.

Serialization key is the existing exact endpoint advisory key (connector_type, endpoint_identity), retaining Gmail's existing connector-classification key mapping so no two independent lock families protect the same endpoint. Before assigning an accepted time, the canonical writer and actual history BEFORE INSERT guard acquire that transaction-scoped endpoint lock and the existing registry row when present. The history guard applies this on parent-routed INSERT, direct child INSERT and COPY; a direct SQL statement is not exempt because it started earlier. After waits complete, the guard assigns received_at = pg_catalog.clock_timestamp() and recording_xid = pg_catalog.pg_current_xact_id(), ignoring caller values. statement_timestamp(), transaction_timestamp(), now(), payload sent_at and a caller/test clock selector never define protected accepted time. The acquired lock remains until the business transaction ends. The returned actual row stamp is then used by the existing registry UPSERT. A writer held across a reader's captured as_of either committed before that reader acquired the endpoint lock or receives its stamp after the reader releases it. Same-endpoint new instances use the same key; a first-registration detail lookup locks its requested key even before a row exists. Distinct endpoints remain independent.

A moving wall clock cannot be independently recomputed for equality in an AFTER trigger. Replace that false integrity rationale with a closed trusted trigger chain. The four trigger-only functions remain stamp_heartbeat_history_row, validate_heartbeat_history_row, derive_registry_heartbeat_coverage and validate_registry_heartbeat_coverage in the owning Switchboard schema. Every entry checks its real TG_RELID/TG_OP/TG_WHEN context against the actual canonical parent/attached child or registry OIDs, its fixed owning schema and trusted function/table owner; copying a function onto a lookalike or TEMP table cannot mint authority. The source installer defines the exact allowed trigger definitions, enabled modes, timing/events, functions, clone parentage and nondeferred state. Before stamping, deriving, validating or certifying a read, inspect the actual parent/children/registry catalogs against that installed closure. Refuse a write or return listening UNKNOWN for an extra unapproved BEFORE/AFTER/deferred trigger, rewrite rule, disabled/missing guard, wrong function/owner, invalid clone, or unprotected partition. The check is not a caller marker, GUC, supplied role, body hash or grant-presence assertion. Trusted existing maintenance is included only by its actual installed definition; do not blanket-allow all migration-owned arbitrary triggers.

Protect that catalog inspection against concurrent ordinary CREATE TRIGGER with transaction-held ROW EXCLUSIVE relation locks on the actual parent, relevant attached children and registry, acquired before the catalog check and accepted/read time. This mode conflicts with PostgreSQL's SHARE ROW EXCLUSIVE trigger-DDL lock while remaining compatible with heartbeat DML ROW EXCLUSIVE locks; it is not an exclusive fleet mutex. Use deterministic relation/endpoint/row ordering in the native paths, re-read actual attachments after locks, and refuse or degrade on a changed/missing required relation. Existing trusted partition maintenance stays outside the canonical primary writer transaction, as today. The reader locks all attached partitions relevant to its requested interval, including any physically retained month used for that read; an unprotected parent or child cannot supply a certified positive or negative. Actual lock reachability under the current API/runtime roles, clone propagation, direct-child behavior, partition maintenance races and absence of cross-endpoint blocking are required PG controls, not proven by this proposal. No privilege is widened if these controls fail.

The history AFTER validator checks actual trusted chain closure, exact current xid, nonfuture post-lock receipt and required identity/body fields; the trusted BEFORE stamp cannot be overwritten by an extra permitted runtime trigger because such a chain is refused. Ordinary UPDATE/DELETE of accepted history, backfilling recording_xid, and TRUNCATE/ALTER/DROP/guard replacement remain refused. It does not pretend to reconstruct the earlier clock_timestamp value from a second clock call. Existing trusted monthly pruning is DDL under its original authority and does not create a runtime bypass. If a runtime role actually owns a protected object or can defeat the closure, preserve the positioned failure and redesign the bounded mechanism; do not declare the trusted-role assumption satisfied.

Before registry heartbeat mutation ignore proposed coverage and derive it only from an exact same-endpoint, same-instance, same-receipt, relevant-body log row whose stamped xid8 is the current transaction, under the closed protected chain. A stale committed matching row is insufficient. First valid pair sets coverage_start to its returned post-lock time; a still-valid prior boundary is preserved. Missing/replaced partition receipts, an unpaired tuple or identity transition clear completeness within that existing write. A later pair starts forward, never backfills a gap. Settings/cursor-only changes preserve a valid unchanged heartbeat boundary and never mint or extend it; marker-only forgery is ignored/refused. AFTER registry validation repeats the exact transition checks under the same closure. Partition OIDs and bounds are read from actual attached catalogs, not names, and old receipts outside the seven-day horizon promise nothing.

Supported legacy registry-only writes remain supported and claim runtime_instance exactly as before, but never certify history. PostgreSQL may acquire their registry row before a BEFORE UPDATE trigger runs: do not add a reverse row-to-endpoint advisory wait to that unpaired path. Clear coverage in that existing write. A direct paired producer must append protected history before its certifying registry write. Reversed registry-first paired work may deadlock/refuse and roll back under ordinary PostgreSQL semantics; it cannot earn completeness. Existing legacy writes need no new transaction/authority declaration. Native correct paths acquire catalog locks, endpoint keys and registry rows in one order. Keep any unavoidable direct reversed-order failure honest and prove that it leaves no accepted pair/marker, while a correctly ordered direct producer and unrelated endpoint succeed.

The source correction makes that refusal deterministic: an unpaired heartbeat tuple mutation takes `pg_try_advisory_xact_lock` on the distinct negative-only `heartbeat-registry-first:<type>:<endpoint>` hash. It never waits while holding the registry row. Failure to take that witness refuses the mutation. The history BEFORE guard checks its own backend's granted bigint advisory key in `pg_catalog.pg_locks` before taking the normal classification/endpoint lock, and raises fixed SQLSTATE 55000 for reversed work. The negative witness neither establishes coverage nor writes a row. Caller-acquired locks can cause refusal only, not positive admission. Transaction end releases it, session unlock cannot erase it, a successful savepoint retains it, and savepoint rollback removes the witness with the rolled-back mutation. Unchanged settings/cursor edits return before creating it; another endpoint has a distinct key. Actual existing SET ROLE controls must prove whole-row/history rollback, session-unlock resistance, both savepoint paths, peer-key interference refusal and correctly ordered/legacy-only/independent-endpoint positives. PostgreSQL's documented transaction-lock semantics support this design; source inspection is not PostgreSQL execution proof.

Handler order: parse the unchanged envelope; ensure current/next partition via the existing serialized maintenance outside the primary transaction; acquire catalog-stability locks, exact endpoint advisory and registry row; for Gmail validate its existing admission/epoch/generation before any log or registry mutation. Refusal returns the unchanged bounded refusal ACK and mutates neither. Admission performs the existing history INSERT RETURNING the actual DB stamp/xid, then existing registry UPSERT with that stamp/capability object, computes deltas from the locked predecessor, COMMITs, and only then returns accepted/classification ACK/server_time. Required append/registry/commit failure rolls back both and yields no adoptable ACK. Connector failure remains nonblocking with normal interval retry and content-blind diagnostics; local successful Gmail contact-query evidence is not demoted. Unknown ACK does not undo a committed pair; the next heartbeat is a new observation and exact Gmail request retirement remains unchanged.

Host clock and trusted administrator are the existing trusted boundary. No hostile clock/admin or restored-history guarantee is invented. Detect available future/regression/invalid-boundary evidence conservatively and return UNKNOWN or restart forward coverage; xid is not a wall-clock oracle. Rollback to legacy code clears/no longer certifies boundaries. All source/time/role/trigger/DDL/late-commit statements here are proposed mechanisms pending actual disposable PG falsification, not execution credit.

## D4. Time keys, SQL projection and wire

Capture one UTC `as_of` and one canonical window after acquiring the relevant registry read/serialization locks. For `24h`, define the exact rolling interval `[as_of-24h, as_of)` and 24 one-hour UTC intervals anchored to that start: bucket i is `[as_of-24h+i*h, as_of-24h+(i+1)*h)`. These are real timestamps and may have nonzero minutes; they are not misleading clock-hour labels. Use generate_series plus interval joins/date_bin with that explicit origin, not date_trunc with positional padding. Relative axis anchors `-24h`, `-12h`, `now` then locate actual window start, midpoint and end truthfully. The final interval ends at the captured as_of; no future time is counted. A currently open calendar-hour diagnostic is separately UNKNOWN and never mistaken for a completed rolling interval. Existing S3 UTC-hour-aligned source keys must either retain their declared source window with truthful computed ranges or be explicitly updated to this same rolling origin in the owning endpoint; do not invent timestamps to make keys fit.

For existing `7d`/`30d` ranges, preserve daily count semantics and return actual UTC day-start keys; do not reinterpret daily rows as hourly slots. For a daily listening verdict, require positive observations for LIVE, and complete closed-day coverage for DEAF; older/partial/partly covered days are UNKNOWN. Retention is MONTHLY partitioning with a nominal seven-day pruning policy. Guarantee no more than the conservative seven-day horizon even if older monthly rows happen to survive. A bucket intersecting that floor, preceding first_seen_at, preceding activation, extending after its captured source cutoff, or intersecting a recording gap is UNKNOWN. Positive retained historical counts are independent and stay usable.

Each structured bucket carries `bucket_start`, `bucket_end`, separate nonnegative ingested/failed/filtered counts (or counts=null with explicit unavailable source), and `listening: live|deaf|unknown` plus a closed reason. Suggested reasons: heartbeat_observed, complete_recorded_gap, current_bucket_open, before_first_seen, before_activation, outside_guaranteed_retention, recording_history_unknown, partition_history_unknown, heartbeat_source_unavailable, receiver_evidence_unavailable, invalid_cached_contract. Metadata carries as_of, canonical window keys/width, count-source availability and heartbeat-source availability independently. Do not expose xid, partition receipts, private endpoints beyond existing fields, error text, capabilities, counters used only for integrity, credentials, or source payloads in the chart DTO/log/metric labels.

Detail counts are generate_series-dense with exact `(COALESCE(source_provider,source_channel), source_endpoint_identity)` for ingestion events and exact `(connector_type,endpoint_identity)` for filtered events. Roster uses the same canonical provider/endpoint predicate and captured window, in a single bounded batch aggregate for all roster pairs, not N+1 detail reads. Heartbeat aggregation is bounded by exact endpoint keys and the same window and index. Sum the independent ingested and filtered series correctly; do not merge skipped traffic into delivered traffic. Summary/detail parity compares requests with the same as_of/window, never independently sliding clocks. Keep current role, archive, soft-delete, auth, replay, checkpoints, incident, costs and fleet-authority rules unchanged.

Remove the four fabricated heartbeat_count/healthy_count/degraded_count/error_count fields from canonical hourly/daily models and corresponding frontend transforms, and from the sibling roster/switchboard/api/models.py hourly/daily DTOs. The latter are used by legacy aggregate /ingestion/volume, not a canonical endpoint liveness source; preserve its real delta-count/hour/day wire behavior without inventing an endpoint=all listening verdict or a dashboard namespace fallback. Do not fake their replacement values. Preserve real counts and unrelated nullable uptime behavior. Add timestamped roster `hourly_buckets`; older numeric arrays may remain temporarily derived from a successful canonical count read solely for non-chart compatibility, but charts never infer keys or listening from them. Cached/old responses lacking compatible window/listening evidence yield named UNKNOWN/unavailable cells rather than synthesizing timestamps or LIVE.

Detail locks the requested exact endpoint key even when its registry row is absent, then retains its existing registry FOR UPDATE/disconnect serialization. Roster fixes one selected exact-pair batch, takes endpoint keys and rows deterministically, and reports that actual batch; a newly created unselected endpoint appears in a subsequent response, never retroactively certifies the selected batch. Both acquire compatible catalog-stability relation locks before checking the complete protected trigger/partition chain and capturing pg_catalog.clock_timestamp() as as_of. Hold catalog, endpoint and row locks through the reads. Use the existing ordinary READ COMMITTED transaction semantics so post-wait queries see the relevant completed endpoint writes. A pre-wait REPEATABLE READ snapshot or serialization failure cannot certify absence; abort/degrade that read rather than reuse its stale snapshot. A held direct history statement stamps after its wait, so it cannot later insert into a reported closed interval merely because statement_timestamp preceded the wait. A reversed/invalid direct transaction cannot certify coverage. Same endpoint/type across new instances shares the key; no sibling key or global fleet lock is substituted. A valid API role that cannot acquire the required existing locks must report UNKNOWN without a new grant. Listening is a committed receiver-observation snapshot, not a provider/physical-availability promise. Count query success remains authoritative. Put an optional heartbeat/coverage query inside a nested transaction/savepoint; catch its expected unavailable exception **outside** the nested transaction so the parent can finish. Record closed degradation metadata, keep the original independently read counts, and verify durability/visibility from another acquisition. Count-query failure yields unavailable counts and no fabricated zero, regardless of heartbeat success. Registry lookup failure/nonexistent/deleted behavior remains its existing 503/404 contract. Roster applies equivalent isolated-source semantics without per-row transactions. Read-only means no dashboard DML, not SET TRANSACTION READ ONLY incompatible with FOR UPDATE.
