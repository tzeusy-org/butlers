# Design

## Source and authority

Use the Health appointment and visit brief recorded through `src/butlers/jobs/health_visit_brief.py` and the current [Health capability](../../specs/butler-health/spec.md). A future file request must carry server-derived owner authority and resolve to a single Health brief the owner is entitled to read. Schedules, appointment text, third-party content, stored links, and other participants carry no file-generation authority. The owner command in `bu-jv1moa.34` can supply the request if that contract is adopted separately.

Pin the exact rendered snapshot, its version or content identity, and the existing per-figure fact attribution before the first provider effect. Preserve stale-feed language, traceability, and the reminder that this is a record rather than medical advice. A changed, pruned, or unavailable snapshot fails the old request before any new effect. A new snapshot needs a separate explicit owner request. Use neutral file names and titles that omit the owner, appointment, clinic, dates, and clinical details.

## Copy and delivery boundaries

1. **Drive.** Reuse the [owner-private target guard and native document tool](../../specs/module-google-drive/spec.md#owner-private-target-guard). Verify the connected account is the approved owner account and its target folder is private and outside a Shared Drive. Apply the existing Health creation mark. Verify the resulting document's private ACL and mark again before export. Any unreadable, changed, or shared target stops further effects. Do not modify ACLs or use a share link to recover. A create that might have committed while its acknowledgment was lost goes to owner review with no second create.
2. **PDF.** Reuse the [effect-keyed PDF export](../../specs/module-google-drive/spec.md#mcp-tool--drive_export_file). PDF generation requires an approved Drive copy as its source. Bind the exported bytes to the approved document identity and version before accepting a PDF. If the existing export path cannot prove that binding across a concurrent edit, stop the stage and settle any incomplete copy under its adopted cleanup policy. A confirmed repeat reuses the recorded artifact only while it is available and authorized. A known export failure leaves an honest record of the private Doc without a PDF or delivery credit. Keep the returned digest and size in the existing attachment handoff. An expired or missing blob refuses delivery instead of silently generating another file.
3. **Owner delivery.** Use the governed owner notify boundary and its resolved Telegram route if the owner approves that copy. A file attachment carries the recorded storage reference, digest, and size. Route failures send nothing to a fallback destination. Count delivery only on acknowledgement of the complete attachment. A partial or uncertain effect keeps a terminal receipt, preserves any prior confirmed copy state, and authorizes no automatic replay.

Reserve one durable owner request before creating any copy. Bind the receipt to the authorized appointment, snapshot, destination account, and effect identity so overlapping work can reuse confirmed stages and cannot duplicate uncertain ones. The implementation plan must account for interruption at each provider boundary, including a provider acknowledgment that arrives just before the database write fails. A recorded success can be returned again. Unknown effects require explicit reconciliation before any new attempt. No receipt changes the existing plain-text brief's delivery timestamp.

Keep clinical content, raw provider replies, credentials, account or chat identifiers, storage references, document links, and identifiers for source facts out of general-purpose telemetry, operator output, and planning evidence. Exact source and copy references live in the restricted receipt alone. The ordinary job and attention results expose closed stages and outcomes. A repeated request rechecks owner authorization and current access before it exposes an existing artifact. Scope all reads and cleanup to the exact authoritative copy identity.

## Owner decision

The [digest retention proposal](../bound-health-visit-brief-retention/proposal.md) classifies the figures as confidential. `bu-yxfwfx` is the owner decision on the database digest's anchor and retention delay. It leaves Drive, the PDF blob, and a delivered Telegram message outside its scope.

Before implementation, record whether the owner permits a Health-owned private Google Doc, a managed PDF blob, and an owner-only Telegram attachment. A decision covering a copy must specify its purpose, storage, retention anchor and duration, who can remove it, and handling for incomplete cleanup. State any provider history, trash, backup, or delivered attachment that Butlers cannot verify as deleted. An indefinite duration requires an explicit decision. A decision to keep this feature text-only leaves it disabled. Product activation is a separate owner-controlled step after implementation evidence.

The reviewed proposal may proceed as planning. Future file generation remains disabled until the owner adopts the exact review artifact and the policy. The scope excludes automatic file generation, clinic recipients, changes to authoritative Health facts, new services, and broader Drive permissions.

## Handoff and verification plan

- Extend `roster/health/tests/test_jobs.py::test_visit_brief` on migrated PostgreSQL for source binding, stale-feed and attribution preservation, no effects for missing authority, overlap, repeated request, and crash-safe settlement. Include the existing terminal partial control and a completed delivery companion.
- Reuse the fake Drive and export fixtures in `tests/integration/test_google_drive_integration.py` for private parent and document checks, the Health creation mark, changed and unreadable permissions, an edit during export, effect-key replays, and export timeout. Assert exact create/export request totals and zero blob writes for a refused or failed export before storage.
- Reuse `tests/core/test_blob_storage.py` for pinned binary integrity, copy-specific cleanup and truthful failure. Exercise the existing owner transport with a fake attachment acknowledgment and observe one outbound request on success, zero on failed access, and no automatic replay after an ambiguous send.
- Root files an implementation successor behind the existing export and classification work (`bu-jv1moa.5`, `bu-jv1moa.23`), the reconciliation checkpoint `bu-jv1moa.16`, and the explicit owner decision, or records owner deferral. `bu-jv1moa.16` already waits on this planning bead, so keep that edge and place its dependency on the later successor.
