# Agent Fleet Playbook

> **Purpose:** Hard-won traps for the agents, coordinators and reviewers that build and land changes in this repository.
> **Audience:** Anyone driving CI, the merge queue, `bd`, worktrees or subagents.
> **Origin:** Moved here from Beads memories (`bd remember`) so that `bd prime` stays small (bu-uxhtox). Each trap states a thing that was true when observed; the date is part of the claim. Rules that already live in `AGENTS.md` are not repeated.

## Merge queue and CI

Landing route: `gh pr merge <n> --squash --auto` enqueues the PR in the GitHub merge queue (see `CLAUDE.md`). The queue is an organization-only feature, which is why the repository lives under `tzeusy-org`; the ruleset requires the non-strict checks `check`, `guards` and `frontend`. Its settings are owner-only (decision bu-6jv1bq).

- **Queue state.** `autoMergeRequest` stays null for queue entries. Read the state with GraphQL: `pullRequest(number:N){ mergeQueueEntry { state position enqueuedAt } }`, then wait for `mergedAt` before closing the review and source beads. A reviewer that has enqueued an exact-head-reviewed PR reports `merge-queued`, not merged.
- **A conflicting PR runs zero CI.** `ci.yml` triggers on `pull_request`, which builds `refs/pull/N/merge`; GitHub cannot build it while conflicts exist, so there are no check runs at all (observed on #3798: total 0, status pending). Any predicate that counts failures or pendings reads that as green. Resolve the conflict first, then push, and assert a minimum check count (7 when observed) and `mergeable != CONFLICTING`. Separately, `migration-chain-main.yml` runs only on push to `main` (under `alembic/versions/**` and the module and roster migration paths), so an Alembic PR gets that check only after it lands.
- **An empty check rollup is not green.** For about a minute after a force-push `statusCheckRollup` is empty and `mergeStateStatus` is `UNKNOWN`. Require positive evidence: the minimum count, every check with a non-empty conclusion, `mergeStateStatus != UNKNOWN`, and the same verdict twice 60 seconds apart. `gh` reports a pending conclusion as `""`, not null.
- **PR-head CI skips shards.** PR-head CI often runs only `check-affected`; the merge group runs every shard. `merge_ok` and CLEAN on the PR head do not prove the full unit lanes passed (#4286 was ejected by a `check-unit-2` failure the PR head never ran). Backend PRs touching shared code need the CI-shaped local lanes from the `AGENTS.md` Test Scope Policy.
- **Reruns.** `gh run rerun <id> --failed` cannot clear a flaky shard: `check-unit` and `check-integration` reload the `ci-inventory` artifact bound to the first attempt and `scripts/check_ci_test_shards.py` refuses with `inventory source/config/attempt mismatch` (exit 2). A partial rerun can also make `check-preflight` fail with `complete eleven-child execution proof unavailable` (`scripts/ci_preflight_reconcile.py`, #4623). Use a full `gh run rerun <id>`, or let the next pushed head run fresh. A cancelled run produces the same preflight message; it is an artifact of the cancel, not a code fault.
- **Cancelling queued runs.** `gh run cancel` on a run whose jobs wait for runners often answers "submitted" and does nothing. `gh api -X POST repos/<owner>/<repo>/actions/runs/<id>/force-cancel` completes it at once; verify with `gh run view <id> --json status,conclusion`. Before cancelling any "queued" run count its job states: `gh run view <id> --json jobs --jq '.jobs | group_by(.status) | map("\(.[0].status)=\(length)") | join(" ")'`. A run stays `queued` while any one job waits, and #4712 looked queued with 16 of 18 jobs done. Only cancel runs that a required later push supersedes.
- **`checks_timed_out` and runner starvation (2026-10-18).** The rule observed was `check_response_timeout_minutes` 60, `max_entries_to_build` 5, ALLGREEN (read it with `gh api repos/tzeusy-org/butlers/rules/branches/main`). Five group runs of about 18 hosted jobs each plus roughly 15 PR runs saturate hosted concurrency; an uncontended group takes 44 to 49 minutes, a contended one exceeds 60, the entry is removed with `RemovedFromMergeQueueEvent` reason `checks_timed_out`, and every group behind it rebuilds. The PR stays OPEN and CLEAN. Read the reason with GraphQL `timelineItems(itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT])`. Remedy: (1) force-cancel stray `merge_group` runs whose `headSha` no longer matches a current queue entry (`git ls-remote origin 'refs/heads/gh-readonly-queue/main/*'`); (2) cancel PR runs whose `headSha` is superseded, after reading their job states; (3) if the head is unchanged, re-enqueue with `gh pr merge <n> --squash --auto --match-head-commit <reviewed sha>`; no re-review is needed.
- **An UNMERGEABLE entry blocks pushes.** A PR the queue marks UNMERGEABLE (a conflict after a predecessor merged) stays queued, and any push to its branch fails with GH006 "Branches that are queued for merging cannot be updated". The coordinator fetches the PR node id (`repository.pullRequest.id`), runs `mutation dequeuePullRequest(input:{id})`, confirms `mergeQueueEntry` is null, and then the author pushes the merge of `main` (plain push) and the reviewer re-checks and re-enqueues. Find the conflicting file early with `git merge-tree --write-tree origin/main <head>`.
- **Polling at scale.** Per-PR `gh` polling of about 85 PRs tripped the GraphQL secondary rate limit on 2026-10-18 while the primary budget showed 4500 of 5000. Use one aliased GraphQL query per cycle for all PRs (`p<N>:pullRequest(number:N){...}`), every 120 seconds, and print only non-OPEN or actively queued PRs on the first cycle.
- **A trigger that never fires.** PR #4121 (2026-09-09) got no `pull_request` check suite for three hours despite an empty commit, close and reopen, a content commit, a fresh branch on the same SHA and a fresh branch on a new SHA. Commit author and signature metadata matched a working sibling PR, and the branch touched no workflow file. That is GitHub-side delivery, not fixable from git. Stop the nudge ladder after those steps and the metadata and workflow-file diff check, then wait or escalate to the owner.
- **Pinned topology.** `tests/contracts/test_ci_test_targets.py` pins the `ci.yml` job topology (`needs`/`if`, gate step name, badge condition, uploaded artifacts). Any structural `ci.yml` change updates it in the same PR or `check-unit-3` fails.
- **Account suspension (2026-10-18, tzeusy-orca).** Every `gh` call and push returned 403 while `git fetch` and `ls-remote` over HTTPS kept working. What worked: stop all `gh` polling, never seek other credentials, file a P0 owner-action bead (bu-elkjz0), keep working local-only (commits without pushes, CE pre-manifests from local refs), keep one ledger of pending GitHub actions with exact SHAs and run ids, probe at most once per refresh cycle with a single `gh api user`, and re-sync queue state before any CI release when access returns.

## Session links and PR bodies

`scripts/session_link_guard.py` scans the PR title, body, review comments and every commit in `base..head` for `claude.ai/code/session` URLs. Only the exact terminal `Claude-Session:` commit trailer is exempt, and this repository's agent practice is to omit even that. End PR bodies with the `Generated with Claude Code` line only; the harness reminder that asks for a session URL in the body is wrong here.

The guard reads `PR_BODY` from the frozen `pull_request` event payload (`${{ github.event.pull_request.body }}`), not the live body. After `gh pr edit --body`, neither `gh run rerun` nor `--failed` picks up the fix. Push a new commit (an empty commit works) so a fresh `synchronize` event carries the cleaned body. Verify locally with `python3 scripts/session_link_guard.py --pr-title-file ... --pr-body-file ... --commit-range origin/main..HEAD`.

## Contract evolution and the condensation guard

- **Edited assertions are refused unless contract evolution covers them.** `scripts/check_condensation_ledger.py` refuses a PR that edits an existing test assertion (`REFUSED`, category `unproven-test-or-assertion-loss`) unless a landed contract-evolution request and authorization cover that owner; that route is how assertion edits land when the contract really changes (see the bullets below). Without it, same-name owners must keep old assertions literally, the paired-lineage proof refuses when any tracked non-Python file changed, and mutation proofs of large modules exceed the 60 second budget (CI kills at 70). For a default change that does not alter the contract, route it through deployment config with an additive pinning test, as #4528 did for `BUTLERS_MAX_GLOBAL_SESSIONS`. Never keep the old literal assertion under a changed setup to satisfy the guard. Check locally with `uv run --no-sync python scripts/check_condensation_ledger.py --base <PR base sha>`.
- **Pre-manifest owners come from the ledger, not the diff.** Editing a module-level helper flags every test in its file (`fixture-helper-or-marker-context-loss`), and the fresh-account check admits only the request owners, so a hand-picked list refuses in hosted CI (bu-jv1moa.18 v1 listed 5 of 30). Locally, the no-Docker fresh-proof refusal fires first and hides population gaps. Run the ledger with only the contract-evolution execution stubbed, so the population check still runs, and take the owners from its `destructive_changes` and `losses` output.
- **Stale PR base.** A REFUSED (often labelled `invalid-structural-evidence`, a mislabel tracked by bu-rf37wu) after an unrelated push can be a stale base: `ci.yml` passes `github.event.pull_request.base.sha`, which a plain push does not refresh. Once a contract-evolution request lands on `main` after that base, the guard demands the PR's files be covered (`unapproved-contract-runtime-input`). Re-run the script with `--base <merge ref first parent>`; PASS there means stale base. `gh pr update-branch <n>` (a merge of `main`, no force-push) advances it (tracked as bu-1bxczh). Merge-queue runs are unaffected.
- **Local refusal can be environmental.** `make check-guards` can print `fresh-contract-evolution-proof-refused` even when `contract_evolution.authorize()` passes, because the fresh proof executes the owner tests at base and head and a Docker-backed owner cannot run on the orca host. Treat it as environmental only after `authorize()` passes, push, and read the hosted `guards` job (#4599 refused locally and passed hosted, 6 of 6 owners).
- **Manifests go stale only on edits.** A manifest goes stale when `main` edits one of its listed input paths (the before-hash moves). New files on `main` never stale it: `authorize()` requires only `pyproject.toml`, `uv.lock`, owner files and ancestor `conftest.py` files (`scripts/contract_evolution.py`). In `merge_group` CI the trusted base is `merge_group.base_sha`, so queue predecessors matter only if they edit a listed path. When a PR merges, diff its files against every in-flight manifest's inputs (#4608 edited `qa/dispatch.py` under #4609's manifest; its new `core_266` did not stale #4615).
- **A CE draft hides the frontend build.** The `guards` job stops at the REFUSED ledger step, so `npm ci`, `npm run lint`, `lint:emdash`, `lint:query-coercion`, knip and `npm run build` never run, and `frontend` and `check` fail only "because guards failed". Real breakage surfaces after the manifest lands (#4603: TS2345 in `create-rule-dialog.tsx`). For a CE draft touching `frontend/`, run lint, knip and build locally in `frontend/` before rating it clean-pending-contract-evolution.
- **Query-coercion gate.** `npm run lint:query-coercion` (`scripts/check-query-result-coercion.mjs`) is separate from `npm run lint`, knip and build. It refuses net-new `?? []` or `?? 0` on a TanStack query's `.data`, `.meta.total` or `.meta.count`. Handle loading and error states explicitly.
- **Review lesson: caches in evidence code.** A "behavior-preserving" cache of path resolution in the condensation proof worker (#4551) was not: the traced subject can retarget a directory symlink mid-run, so retained resolutions made real tracer arcs vanish while the proof reported `complete=true`. When reviewing speedups in `scripts/condense_evidence.py` or any coverage path, treat every cache that outlives a single call during subject execution as evidence-weakening until a retarget or mutation test proves otherwise. Timing gathered with a defective fast path does not carry over.

## Specs and OpenSpec

- **Archived prose is frozen.** Editing a baseline spec under `openspec/specs/` must keep every sentence and scenario line an archived change declared delivered, byte for byte (`scripts/check_archived_requirements_landed.py`). `openspec validate --strict` and `check_spec_overwrites.py` do not catch this. Express amendments additively (a new SHALL sentence, AND clause or scenario), and run the script on any spec edit. Additive edits still change the requirement hash, so contract-evolution manifests bind them (hit on #4598 and #4599).
- **Archiving.** `openspec archive` supports early-sync: hand-edit baselines first, then archive; identical MODIFIED blocks, already-applied RENAMED and already-removed REMOVED are no-ops, which bypasses the "current spec contains scenario(s) not present" abort. Removing a whole capability: archive refuses a spec left with zero requirements, so move the REMOVED delta dirs aside, archive, `git rm` the capability dirs, then copy the REMOVED deltas back into the archived change (the landed guard honours REMOVED only from archived changes). Text in an undated archived MODIFIED block can never be superseded.

## Migrations

See also [Migration Patterns](../data_and_storage/migration-patterns.md).

- **Revision numbers collide across in-flight PRs.** Choosing the next `core_NNN` from `git ls-tree origin/main -- alembic/versions/core/` is not enough when several workers run at once: `core_216` and then `core_218` were each claimed by two workers on 2026-09-05, the second time as two different filenames declaring the same `revision` string, which a routine rebase does not fix. Before assigning a number, grep `revision = "core_` across every open PR's migration files (`gh pr view --json files`) and every active worktree, and take one past the highest claimed anywhere.
- **No `CONCURRENTLY` on shared tables.** A transactional `ALTER TABLE ADD COLUMN` followed by `CREATE INDEX CONCURRENTLY` (in `autocommit_block()`) on a shared cross-butler table such as `public.dashboard_messages` deadlocks under `tests/migrations/test_runtime_attention_outbox_migration.py::test_core_chain_serializes_global_runtime_attention_downgrade_and_reapply_across_processes`, which upgrades the core chain for two butler schemas at once. The circular wait can involve an unrelated, already-merged plain `ALTER TABLE` in another migration (here `core_213_dashboard_messages_sources.py`), so a `pg_advisory_lock` scoped to the new migration does not help and cannot be retrofitted. Use plain `CREATE INDEX IF NOT EXISTS` for DDL on shared public tables (as `core_006`, `core_210`, `core_213` do), and grep the whole migration history for other DDL on the same table first.

## Shell, processes and git

- **A full gate cannot run in the foreground.** A full pytest gate takes 21 to 25 minutes; the Bash tool caps at 600000 ms and kills the process tree, leaving a log that simply stops with no summary and no `## pytest-gate exit=` receipt. `pytest_gate.py`'s own-session trick survives the turn ending, not the tool timeout. Start it detached and poll the log for the sentinel; a missing sentinel is UNKNOWN.
- **Wait on exit, not on log text.** A Monitor with `tail -n 5 full.log | grep -qE 'passed|failed|error'` reported "3821 passed" for a run at 49%. Warnings and ERROR lines appear long before the summary. Wait on the process, then read the summary, and sanity-check the magnitude (the non-e2e suite was about 14800 tests and 20 minutes).
- **`pgrep -f` waiters match themselves.** `until ! pgrep -f 'pytest_gate.py run'; do sleep 20; done` never ends, because the waiter's own argv contains the pattern; stale waiters then poison "is a gate running?" checks. Record the PID at launch and wait with `kill -0 $PID`, or use a bracket class (`pytes[t]`). The probe only exposes the bug after the target has exited, so test it that way. Scoping `pgrep` to a worktree's own `.venv/bin/pytest` keeps another worktree's identical command from ending your wait.
- **Local pre-push.** Run `PYTHONDONTWRITEBYTECODE=1 uv run --no-sync python scripts/pre_push.py check --base origin/main` through the project venv (system `python3` lacks pytest, so `fresh-inventory-partition-budget` exits 2). It refuses with `guard-source-side-effect` if the tree changes during the run, including a stray `scripts/__pycache__`: commit first, delete stray caches, edit nothing while it runs. In agent worktrees `core.hooksPath` is unset and no hook is installed, so the explicit check is the gate; overriding `core.hooksPath` is a guard dodge.
- **`git rebase --continue` commits conflict markers.** Neither it nor the CI guards check for them (a Markdown file with `<<<<<<< HEAD` passes every guard). Capture and assert: `N=$(grep -c '^<<<<<<<' file || true); test "$N" -eq 0 || exit 1`, and `git grep -e '^<<<<<<<' -- .` before every push. Do not encode an unmeasured precondition into a resolution script; print the sides' lengths or hashes first.
- **Test merges from the root repo.** `git clone` from a local path clones local `main`, not `origin/main`. Run `git merge --ff-only origin/main` in the root repo (HEAD stays on `main`) immediately before cloning for a test merge, or a stale `main` yields a false CONFLICTING diagnosis.
- **Stale local `main` misleads diffs.** A recycled reviewer worktree can have a local `main` many commits behind. `git fetch origin main` first and diff `origin/main...HEAD` (#4033 showed 5700 unrelated lines before the fetch).
- **Merge-base patch ids.** A patch-id comparison must diff the PR head against its merge-base with `main`, not against current `main`, which folds in the inverse of everything landed since (#3877 read false RED at `mb=513e0f2e6`, identical at the merge-base): `mb=$(git merge-base $HEAD $BASE); git diff-tree -p $mb $HEAD | git patch-id --stable`.

## `bd`

- `bd list --json` applies a default limit of 50, so absence from it is not evidence a bead is missing. Pass `--limit 5000`, or confirm with `bd search <text> --json`.
- `bd show <id> --json` returns every dependency as a complete issue object (about 2k tokens for one parent id). Project it: `bd show <id> --json | jq -r '.[0]|"\(.status) deps=\((.dependencies//[])|map(.id)|join(","))"'`. A `pr-review-task` child whose only dependency is an in-progress parent epic reports `blocked` with an empty `blocked_by` and never appears in `bd ready`; the parent-child edge is the blocker and the coordinator can dispatch it by id.
- `bd create --parent <epic>` copies all of the epic's labels, including `complexity:epic`, onto the child (two complexity labels confuse model-tier mapping). Create with `--no-inherit-labels` and pass labels explicitly, or `bd update <id> --remove-label complexity:epic`.
- `bd list --all --limit` misses beads; use `bd export` to count notes.
- A review bead created with its own `external_ref` (`gh-pr:N`) is not read by the old review-context helper, which looked only at the implementation bead; keep `external_ref` on the original bead (`AGENTS.md`) and use `gh pr view` directly if a helper reports `missing-pr-number`.
- Read a bead's full notes (`bd show <id> --json | jq .[0].notes`) before dispatching it, even with a complete dossier design: an earlier coordinator may have left a stamp declining dispatch (bu-2jtfw.9, 2026-09-06). Re-verify the cited concern rather than honouring or ignoring it blindly; if proceeding despite a missing governing spec, require the implementing PR to add the spec.
- Before excluding an epic lane, read its release-gate bead (`bd show <gate-id>`); owners close gates asynchronously and a note written earlier goes stale silently (all four 2026-09 pursuit gates had closed by 2026-09-09). Ready children are claimed within minutes by concurrent coordinators, so expect `already claimed` and take the next sibling.

## Coordinators, subagents and worktrees

- **Talk to a named subagent with `SendMessage({to: <name>})`.** Calling the Agent tool again with the same name silently spawns a context-free duplicate (`<name>-2`) while the original sits unaware; `TaskStop` the duplicate and message the original. Address an in-process subagent by its name (dots normalised to dashes: `bu-istke.4` is `bu-istke-4`), never by the background task id in a check-in listing; a task id returns "No agent named ... is reachable" plus the misleading rider "session list was too long", and `ListAgents` shows only peer sessions, so an empty listing is not evidence a worker is gone. Check the worktree (commits, dirty state, remote) for what was actually done.
- **A subagent that ends its turn on "waiting on CI" goes idle and never wakes** unless it started a background watcher (`gh run watch <id> --exit-status`). Check `pgrep` for its watcher and `gh pr view` for `autoMergeRequest`, and either own the CI watch or tell it to start one before idling.
- **Reviewer worktree reuse.** Do not hand a "completed-pr-opened" worker's worktree to a reviewer while the worker still has an unprocessed coordinator message (a queued renumber instruction made bu-0ynlk-9 push a new head while the reviewer was checked out on the old one). Tell the worker "PR opened, do not touch this worktree again", and route any later fix to the reviewer. Before `git worktree remove` on a merged review bead's worktree, confirm its lane has no newer review in flight.
- **Never delete lane scratch directories** in the shared session scratchpad, even when the name looks like a merged PR (a lane's live base clone was deleted and orphaned its scratch worktrees). Ask the owning lane to prune. Lanes keep scratch clones and `HOME`s under `/home/orca/.tmp/<lane-or-bead>/` (disk), not the `/tmp` tmpfs (32G RAM-backed and inode-limited).
- **Closing a source bead.** A bare `gh pr view --json state` of MERGED proves only that the PR landed. With the merge queue, wait for `mergedAt` and read the reviewer's report before closing the source bead.

## Development environment

- **butlers-dev runs on k3s** (namespace `butlers-dev`, Helm release `butlers`, chart `deploy/helm/butlers`) since 2026-10-02, not Docker Compose. Ship a committed change with `bws run --project-id $BWS_PROJECT_ID -- make ship-dev` from `deploy/helm/butlers`; migrations run in the `dashboard-api` init container. Never start `./scripts/compose.sh` in dev mode alongside it: both would drive the same live database, schedulers and connector sessions. Debug with `kubectl -n butlers-dev logs deploy/<name>`. See [Kubernetes Deployment](kubernetes-deployment.md).
- **The `orca` agent user cannot deploy dev.** `scripts/k8s/deploy-dev.sh` builds images with local Docker and `orca` is not in the `docker` group, so it fails with "permission denied while trying to connect to the docker API" and Helm then fails at template time with `image.tag is required` (no release revision is created). Release CI builds `ghcr` images only on tags, so no prebuilt tag exists for a `main` SHA. Hand dev deploys to the owner; do not work around it.
- **Dev has no `DASHBOARD_API_KEY`,** so agents cannot call `/api/settings/models` POST or PUT. To change the live dev model catalog, mirror the handlers in SQL through `dev-psql.sh` in one transaction: `INSERT`/`UPDATE public.model_catalog` (`updated_at = now()`) plus one `public.audit_log` row per changed row (action `model.create` with `note=<alias>` or `model.update` with `note=<changed fields>`, `target=<id>`, `result='success'`, an actor such as `claude-host-operator`). Never delete rows that have `model_dispatch_attempts` or token ledger history (it cascades); disable them. Insert new rows at lower priority first: the hourly verify sweep probes enabled rows, and `last_verified_ok=false` excludes a row from routing until the next sweep. `codex exec` does not apply a model's catalog `default_service_tier`; only the TUI does (codex 0.159.2).

## Pursuit operations

Pursuits are the multi-agent research runs recorded in [`docs/redesigns/pursuit-ledger.md`](../redesigns/pursuit-ledger.md).

- **Number a run from the ledger.** Read the ledger `Runs` table and the open PRs touching `docs/redesigns/pursuit-ledger.md`, not just `main`. Run 20's working files and bead notes call it run 19 because the run started before run 19 (QA remediation) was noticed in the ledger, and runs 21 (JARVIS architecture, #4589) and 22 (backlog, #4588) collided on 2026-10-17; the later session renumbered. Working files and bead labels may still carry the old number.
- **A pursuit bead is releasable only when `bd lint <id>` is clean** and it carries `--design` and `--acceptance`; description prose never dispatches. Runs 09 and 10 were filed with null design and acceptance and the coordinator readiness gate skipped all 30 for a day.
- **Filing traps (run 20).** Owner decisions listed only in a `[HOLD]` gate's description become untracked when the owner closes the gate: file each as an owner-assigned decision bead at filing time, with `blocks` edges to moves whose first slice needs it. Folded design text keeps each source agent's local "move N" numbering: rewrite cross-references to bead ids before filing. Encode first-slice prerequisites as `blocks` edges and leave later-slice waits in prose, or `bd ready` over-reports. File bugs and decisions standalone, outside the gate.
- **Run mechanics.** Write deep-design and critic briefs from the durable harvest; keep at most 3 agents in flight; verify and file lens security findings during the run instead of deferring them (run 20: bu-svqpzo.9 to .12); a frugality clause in the agent briefs halved per-agent cost (run 15: 22 agents, about 2.4M subagent tokens); budget the dossier under 25 KB and its data JSON under 500 KB from the start (cap audit strings, keep title, severity and evidence). Surface auditors need a minimum-depth rule or they stop at `git log`. Check open draft PRs that write shapes the plan changes (draft #4574 wrote the status enum that run 21's moves replaced). Staggered batches wake at 55 minutes (`ScheduleWakeup` 3300 s), not 60, so each tick lands inside the one-hour prompt-cache TTL (owner instruction, 2026-10-06).
- **Resuming across sessions.** `resumeFromRunId` works only inside the session that started the run. From a new session, give the workflow script `args.from` (skip batches below it) and list both sessions' `subagents` and `workflows` directories in the state file's `transcript_roots` so `harvest.py` finds every journal; the durable harvest file keeps this lossless (run 18).
- **Post-hoc review lessons (runs 01 to 10, 2026-10-08).** Runs 01 to 04 lacked acceptance criteria and closed on merge; reviewer bundles must also include beads that lack a parent link (seven run-05 beads had none); a "do not close without owner post-merge disposition" hold is cleared by explicit owner approval.
