## Epic L — Restore receiver-derived fleet liveness

**Create:** “Restore receiver-derived fleet liveness”; type `epic`; priority P1; label `complexity:epic`. Six children: L1–L4, LR, LP.

**Description:** Restore durable routing across multiple registry TTLs after owner authentication began rejecting daemon heartbeat POSTs. Governing CP requirements: `REQ-butler-control-plane-liveness-001` Receiver-derived daemon observation, `-002` Separate routability dimensions, `-003` Provenance-safe quarantine migration, `-004` Bounded stale-route recheck, `-006` Heartbeat POST retirement, `-008` Shared bounded probe authority across processes; `REQ-butler-base-spec-002` Instance Facts Internal Interface, `-003` Butler as Architectural Primitive, `-004` Staffers vs Domain Butlers; `REQ-butler-switchboard-002` Route eligibility uses separated control-plane facts. QA, owner attention, and deployment readiness are owned by Epic Q.

**Design:** Add separated representation and durable monotonic boot epochs, observe exact Git-roster daemon endpoints under a separately supervised Dashboard controller, compare shadow eligibility, let Switchboard perform its own bounded stale-route probe through the same database-reserved sequence/CAS verifier, cut over route decisions, then retire the obsolete POST. One trusted internal backend network is the adopted topology; no anonymous auth exemption or new service key. Keep owner policy and latest epoch restrictive on rollback. Children share the registry state machine and therefore serialize representation, observer, enforcement, and retirement.

**Acceptance criteria:** Routability remains true after multiple TTLs with valid current-generation daemon responses; stale targets recover via one bounded receiver probe without restart; owner quarantine and incompatible targets remain ineligible; malformed, old-generation, wrong-endpoint and observer-failure evidence fails closed; the protected dashboard API rejects legacy writes. LR records code and real-PostgreSQL/auth-enabled evidence for every listed requirement; LP publishes the epic compliance report. The named nearest seams are `roster/switchboard/tests/test_tools.py`, `roster/switchboard/tests/test_route_transport_outcomes.py`, and `tests/core/test_liveness.py`; behavior tests are the gate. Expected net case delta across L1–L4: about +10–16 focused scenarios, adjusted down when current tests already execute them. RFC/topology and rollback documentation are delivered by children and checked in LR; rollback retains L1 policy provenance.

### L1 — Separate fleet state and migrate quarantine provenance

**Doctrine:** `about/heart-and-soul/vision.md` Rules 4–5 require correct routing and reliable operation; `about/heart-and-soul/security.md` requires narrow runtime authority.

Outcome is an additive representation and deterministic provenance migration; route authority stays on the old projection until L3. Non-goals: probe networking, scheduler policy, or clearing a quarantine on restart.

**Design:** Own Switchboard registry migration, `roster/switchboard/tools/registry/{registry,sweep}.py`, operator policy persistence, and legacy `eligibility_state` read projection. Store observation, policy, compatibility, durable monotonically increasing boot epoch, database-reserved probe sequence, and provenance evidence separately. Narrow boot registration allocates and commits the successor epoch before it can advertise readiness; an old or absent epoch never becomes current after rollback. Classify proven TTL sweeps versus audited owner actions; classify undecidable rows `review_required`. Audit every existing registry writer/reader at this seam and hand the enforcement inventory to L3. Rollback preserves restrictive policy/provenance/latest epoch and the old projection; no schema drop while any reader remains.

**Acceptance criteria:** (1) Real migrated PostgreSQL preserves owner quarantine through probe-like, registration, route-success, restart, migration rerun, and rollback writes; TTL-derived rows remain observation only and ambiguous rows stay unroutable. (2) Concurrent/restarted boot registration allocates strictly increasing committed epochs; an older process or rollback without the current epoch cannot advertise acceptance or renew routing, even with a higher probe sequence. ## Materialization and completion checks

Create parents, then children in dependency order; stamp each complexity label and `reconciliation` on LR/QR/DRc/HR. The report child is last in execution order. The Beads-writer reference calls the reconciliation child “last” because it does not account for project-direction's separate epic report; preserve one reconciliation per epic with all implementation dependencies, followed only by the report. Run `bd lint`, `bd dep cycles --json`, `bd dep tree` for each epic, `bd show` readback for all structured fields, and a fresh dedupe/cohesion scan before marking packets runnable. If active PRs or Beads now own a surface, merge or serialize the packet rather than creating a second owner.

At closeout, each reconciliation tests requirement coverage against current code, instruments, and real behavior; no green guard or test name alone proves coverage. Its worker reports missing/partial findings to the coordinator rather than mutating Beads. Each report supplies a spec compliance matrix and VISION mandate callback. No epic closes with an in-scope mandatory requirement partial, contradicted, or deferred without an approved spec amendment. Historical H3 remains an owner gate; no automation may infer approval from specification adoption.
